# 웹 프로토타입 툴 조사

> 조사일 2026-09-06 · 물음 : 「AI 가 빨리 만들고, 사람이 브라우저에서 바로 노는, 쓰고 버릴 게임 프로토타입」을
> 어떤 구조와 도구로 할 것인가.
> 관련 : `Tools/GamedesignTool/Docs/Guide/기획절차.md` 5·6단계 (거친 프로토타입 묶음 → 몰아서 검증)

## 한 줄 결론

**라이브러리를 고르지 말고 「단일 HTML 파일 + 순수 JS」로 시작한다.** 우리 게임의 물음은 대부분
숫자와 선택(합성 확률·골드·대기 시간)이라 그림 엔진이 필요 없다. 네모가 움직여야 하는 물음이 나오면
그때만 **LittleJS 를 CDN 한 줄**로 얹는다. 툴은 새로 만들지 말고 **폴더 규약 + 목록 페이지 하나**로 시작한다.

## 추천 구성

| 무엇 | 왜 | 대안 |
| --- | --- | --- |
| 프로토타입 하나 = **HTML 파일 하나** (CSS·JS 인라인) | 빌드 없음, 더블클릭으로 열림, 통째로 지우면 끝 | 폴더 하나 (그림·데이터가 붙으면) |
| 화면은 **HTML 버튼·표·숫자** | 우리 코어 루프가 숫자다. 캔버스 그리기 코드가 통째로 사라진다 | 캔버스 (움직임이 물음일 때) |
| 움직임이 필요하면 **LittleJS** `<script>` 한 줄 | 의존성 0, MIT, 문서가 「API 가 작아 LLM 이 잘 짠다」고 대놓고 말한다 | Kaplay (더 쉬움, 대신 파일 서버 필요) |
| 프로토타입마다 **`meta` 한 덩이** (물음 · 판정 기준 · 결과 칸) | 기획절차 4단계의 「만들기 전에 적는 기준」을 파일 안에 붙들어 둔다 | 문서에 따로 적기 (흩어져서 잃어버림) |
| **자동 플레이 버튼** (N일 빨리 감기 + 그래프) | 혼자 30분 눌러 보지 않아도 수치가 고이는지 보인다 | 스프레드시트 |
| 기록은 **localStorage → JSON 내보내기 버튼** | 서버 없이 클릭 수·머문 시간·멈춘 자리를 남긴다 | 없음 (기억에 의존) |
| 목록은 **`Prototypes/index.html`** 하나 | 주말에 링크 하나 열고 몰아서 논다 | 파일 탐색기에서 하나씩 열기 |
| 툴은 **안 만든다** (3장 참고) | 만들 것이 20줄짜리 목록 생성 스크립트뿐이다 | 두 번 아쉬우면 그때 ProtoTool |

## 1. 웹 게임 라이브러리 비교

우리 잣대는 넷이다. ① AI 가 짧게 틀리지 않고 짜는가 ② **빌드 없이 파일 하나로 열리는가**
③ 숫자 중심 루프(액션 아님)에 맞는가 ④ 배우는 비용.

| 이름 | 무엇 | 장점 | 단점 | 우리에게 | 출처 |
| --- | --- | --- | --- | --- | --- |
| **순수 HTML/CSS/JS** | 라이브러리 없음. 버튼·표·`setInterval` | 의존성 0, 파일 하나, AI 가 가장 안전하게 짬. 로컬 파일 그대로 열림 | 움직이는 그림은 직접 짜야 함 | **◎ 기본값** | [DEV: 단일 HTML 파일 시뮬레이션 게임](https://dev.to/idevgames/i-built-a-real-time-simulation-game-in-a-single-html-file-without-react-or-custom-javascript-262p) |
| **LittleJS** | 작고 의존성 없는 2D 엔진 (WebGL2+Canvas2D) | MIT, `<script src=…littlejs.js>` 한 줄로 됨. **문서가 「API 가 작아 LLM 이 좋은 결과를 낸다」고 명시**. js13k 분기는 7KB | 자료가 Phaser 만큼 많지 않음 | **○ 움직임이 필요할 때** | [LittleJS GitHub](https://github.com/KilledByAPixel/LittleJS) |
| **Kaplay** (옛 Kaboom) | 초보 친화 2D 라이브러리 | 셋 중 배우기 가장 쉬움. 잼·프로토타입용으로 꼽힘. CDN 태그 지원 | **로컬 파일을 그냥 열면 안 되고 서버로 띄워야 한다.** 커지면 성능 한계 | △ | [Phaser 비교글](https://phaser.io/news/2026/04/phaser-vs-kaplay-vs-excalibur-2d-web-game-framework) · [Kaplay 설치 문서](https://kaplayjs.com/docs/guides/install/) |
| **Phaser 4** | 가장 큰 HTML5 게임 프레임워크 | 성능·사파리 호환 안정. 2026-04 v4 정식 | 우리 규모엔 과하다. 씬·로더 뼈대 코드가 길어짐 | × (버릴 코드엔 과함) | [Phaser 비교글](https://phaser.io/news/2026/04/phaser-vs-kaplay-vs-excalibur-2d-web-game-framework) |
| **Excalibur** | TypeScript 기반 2D 엔진 | API 가 군데군데 더 간결. 브라우저 디버그 확장 | 자료 적음. 우리 물음과 무관 | × | 같은 글 |
| **PixiJS** | 렌더러(엔진 아님) | 그림 많이 뿌릴 때 빠름 | 게임 뼈대는 직접. 프로토타입엔 짐 | × | [JS 렌더링 벤치마크](https://github.com/Shirajuki/js-game-rendering-benchmark) |
| **p5.js** | 창작 코딩 라이브러리 | 초보·디자이너 친화, 자료 많음 | **API 가 넓고 얕아 숙련 프로그래머는 곧 답답해한다.** 캔버스를 쓸 거면 순수 캔버스로 충분 | △ | [p5 vs 캔버스](https://davidmatthew.ie/p5js-vs-html-canvas/) · [p5 게임 프로토타이핑](https://markdenardo.medium.com/game-prototyping-using-p5-js-86b43ca179c3) |
| Kontra · Litecanvas | 초소형 엔진 | 크기 제한 대회용으로 꼽힘 | 자료 적음 | △ | [벤치마크 저장소](https://github.com/Shirajuki/js-game-rendering-benchmark) |

**정리** — 라이브러리 선택은 우리 물음에 거의 영향이 없다. 「합성 확률이 재미있나」는 버튼과 숫자로 답이 난다.
**엔진을 얹는 순간 뼈대 코드가 늘고, 늘어난 코드는 버리기 아까워진다** (기획절차 5단계의 함정과 같은 이야기다).

> 주의 : 로컬 파일(`file://`)로 열면 `fetch`·ES 모듈·CDN 일부가 막힌다. **JS 를 HTML 안에 인라인으로 넣으면**
> 대부분 그냥 열린다. 안 되면 `python -m http.server` 한 줄이면 된다.

## 2. 그림 없는 「숫자 프로토타입」 방식

### 왜 이게 맞나

- 프로토타입은 **엔진 밖에서 하는 것이 원칙**이라는 이야기가 반복해 나온다. 「점수 체계가 되는지는
  엑셀이나 종이 프로토타입이 똑같이 잘 답한다」. — [gamedesignskills](https://gamedesignskills.com/game-design/video-game-prototype/)
- 다만 **손맛(game feel)** 이 물음이면 종이·표로는 답이 안 난다. 「FPS 의 손전등 감각을 종이로 시험하는 것은
  방법이 아니다」. — [GMTK: 프로토타이핑의 요점](https://gmtk.substack.com/p/whats-the-point-of-prototyping)
- 한 번에 **한 가지 기능만** 시험하라는 조언도 공통이다. — [AIE: 종이 프로토타입](https://aie.edu.au/articles/develop-your-game-design-skills-using-paper-prototypes/)

### 어떻게 짜나 (방치형 게임 방식 그대로)

방치형·증분 게임은 **버튼 하나 누르면 숫자가 오른다**가 전부인 구조다. 우리 농장·합성 루프와 모양이 같다.

| 조각 | 만드는 법 | 근거 |
| --- | --- | --- |
| 자원 표시 | `<span>` 에 숫자, 0.1초마다 다시 그림 | [kastark: 증분 게임 만들기](https://kastark.co.uk/articles/incrementals.html) |
| 행동 | `<button onclick=…>` 하나. div·span 어떤 것이든 됨 | 같은 글 |
| 자동화 | 「관리인」을 사서 클릭을 자동으로 | [Machinations: 방치형 설계](https://machinations.io/articles/idle-games-and-how-to-design-them) |
| 균형 잡기 | **비용 지수·기본값 한 줄만 바꿔** 빠르게/느리게 | [kastark](https://kastark.co.uk/articles/incrementals.html) · [첫 증분 게임의 교훈](https://www.gamedeveloper.com/design/lessons-of-my-first-incremental-game) |

**「균형 잡기가 개발의 큰 몫이고 어렵다」**는 것이 방치형 개발자들의 공통 후기다
([첫 증분 게임의 교훈](https://www.gamedeveloper.com/design/lessons-of-my-first-incremental-game)).
그래서 수치는 **파일 맨 위 상수 한 덩이**에 모으고, 화면 위에 슬라이더로 빼 두면 사용자가 놀면서 바로 돌린다. (의견)

### 자동 플레이 봇

「30일 돌려서 골드가 고이나」 같은 물음은 사람이 누를 필요가 없다. **같은 로직을 루프로 N일 돌리고
꺾은선 하나 그리는 버튼**을 붙이면 된다. 유료 도구인 Machinations 가 하는 일(자원 흐름 시뮬레이션)의
아주 작은 판이다 — 우리는 이미 코드가 있으니 그 코드를 빨리 감기만 하면 된다. (의견 · Machinations 근거는 6장)

## 3. 프로토타입 묶음 구조

### 찾은 것 / 못 찾은 것

- **「프로토타입 갤러리」의 정해진 표준·오픈소스 도구는 못 찾았다.** itch.io 가 사실상 그 자리를 차지하고 있고
  (웹 프로토타입 태그 목록 페이지), 개인 폴더 구조를 다룬 문서는 검색으로 나오지 않았다.
  — [itch.io 웹 프로토타입 목록](https://itch.io/games/platform-web/prototypes)
- 반대로 **「한 화면에 다 두는 것이 프로토타입 속도를 만든다」**는 연구는 있다. CHI 2025 논문 *All in One*
  (Godot 개조판 **Pronto**) 은 게임 로직을 씬 위의 연결선으로 그려 **모든 부분에 한 걸음에 닿게** 했고,
  「복잡한 프로젝트로 커질 가능성을 버리고 접근 속도를 산다」는 맞바꿈을 대놓고 택했다.
  — [ACM](https://dl.acm.org/doi/10.1145/3706598.3714251) · [ResearchGate](https://www.researchgate.net/publication/391269893_All_in_One_Rapid_Game_Prototyping_in_a_Single_View)
  우리에게 주는 교훈 : **파일을 쪼개지 마라.** 한 프로토타입은 한 파일이다.

### 우리가 쓸 모양 (제안)

```
Prototypes/
  index.html                  ← 목록. 카드마다 제목·물음·판정 기준·상태(미검증/통과/불통)
  protos.json                 ← 목록의 재료. 각 프로토타입의 meta 를 모은 것
  2026-09-13-합성확률/
    index.html                ← 프로토타입 본체 (CSS·JS 인라인)
    결과.md                   ← 사용자가 논 뒤 한 줄씩
```

각 `index.html` 맨 위에 이런 덩이를 둔다. 사람이 읽고, 목록 생성기도 읽는다.

```html
<script type="application/json" id="proto-meta">
{ "물음": "합성 결과가 확률로 갈릴 때 한 번 더 하고 싶어지나",
  "기준": ["멈추지 않고 5분", "다음에 뭐하지 하고 멈춘 횟수 2회 이하", "한 판 더 생각이 든다"],
  "만든날": "2026-09-13" }
</script>
```

### 플레이 기록 남기기

서버 없이 되는 선까지만 한다.

| 남길 것 | 방법 |
| --- | --- |
| 클릭 수 · 어떤 버튼을 몇 번 | 전역 카운터 → `localStorage` |
| 멈춘 시간 (3초 넘게 아무것도 안 누름) | 마지막 입력 시각과 지금 시각 비교 |
| 총 논 시간 · 몇 분에 껐나 | `beforeunload` 에 기록 |
| 내보내기 | **「기록 내보내기」 버튼 → JSON 파일 저장** |

- localStorage 를 JSON 으로 내보내는 방식은 흔히 쓰인다 (도메인 넘겨 옮길 때도 쓰는 방법).
  — [FirstLook: 플레이테스트 도구 정리](https://firstlook.gg/blog/best-playtest-tools-game-studios/)
- 남이 놀아 주는 단계가 오면 **PlaytestCloud** 는 HTML 프로토타입을 링크 붙여 올릴 수 있고, 세션마다
  키 입력·마우스 이동·콘솔 로그를 시각 표시와 함께 남긴다. **Pretty Good Playtesting** 은 OBS 로 화면을 묶어
  녹화하고, 시간표가 붙은 이벤트를 보내는 API 를 로드맵에 두고 있다.
  — [PlaytestCloud](https://help.playtestcloud.com/en/articles/1290649-playtesting-an-early-prototype-of-your-game) ·
  [pgpt.dev](https://pgpt.dev/) · [FirstLook 정리](https://firstlook.gg/blog/best-playtest-tools-game-studios/)
  **지금 우리에겐 필요 없다** — 노는 사람이 사용자 한 명이다.

### 「한 파일 몇 줄까지 AI 가 안 틀리나」

**정확한 숫자를 말하는 근거는 못 찾았다.** 대신 방향은 일치한다.

- 깨지는 곳은 「파일 하나가 커서」가 아니라 **파일 여럿에 걸친 의존이 얽힐 때**다.
  — [Augment: 여러 파일 리팩터링이 깨지는 이유](https://www.augmentcode.com/tools/enterprise-multi-file-refactoring-why-ai-breaks-at-scale)
- 문맥에 넣은 모든 줄은 다른 줄과 **주의를 두고 경쟁**한다. 길어질수록 규칙이 무시된다.
  — [문맥 파일 관리](https://www.freecodecamp.org/news/how-to-manage-context-files-in-your-codebase-and-get-better-agent-output/)
- 그래서 해법은 **한 에이전트가 전체를 머리에 담을 수 있는 크기로 쪼개는 것**이다.
  — [멀티에이전트 코딩](https://shipwithai.io/blog/multi-agent-ai-coding)

**우리 눈금 (의견)** : 프로토타입 하나는 **300~600줄 안**. 넘어가면 물음이 두 개 섞인 것이니 프로토타입을 쪼갠다.
우리 저장소 규칙에도 **로컬 Qwen 은 200줄 넘는 생성 금지**가 이미 실측으로 적혀 있다 (`CLAUDE.md`) —
프로토타입 본체는 Opus 나 Flash-Next 가 짠다.

| 재사용됨 | 재사용 안 됨 |
| --- | --- |
| **수치표** (합성 확률·가격·성장 시간) — JSON 한 파일로 두면 양쪽이 읽는다 | 화면 코드 전부 |
| **규칙 문장** (「재료 2 + 골드 + 시간 → 결과 1」) | 입력·연출·애니메이션 |
| 균형 잡힌 곡선의 **모양**과 판정 결과 | JS 코드 자체 |

- Unity 쪽 정석은 **ScriptableObject 는 수치 통, 바깥과 주고받는 것은 JSON** 이다.
  ScriptableObject 로 편집기에서 쓰면서 값을 JSON 으로도 들고 있는 이중 직렬화 패턴이 흔하다.
  — [JSON vs ScriptableObject 비교](https://medium.com/@krmsrn/json-vs-scriptableobjects-in-unity-a-technical-comparison-ae3d2efd59a9) ·
  [Unity 공식: 데이터와 로직 분리](https://unity.com/how-to/separate-game-data-logic-scriptable-objects)
- 게임 데이터를 JSON 에 두고 그것으로 ScriptableObject 를 만들어 주는 도구도 있다 (Charon).
  — [Charon Unity 플러그인](https://gamedevware.github.io/charon/unity/overview.html)
- 우리 규칙(`AGENTS.md` 10항)과도 맞는다 : **ScriptableObject 는 수치 데이터 통으로만 쓴다.**

**그래서 제안** : 프로토타입의 수치를 `Prototypes/<이름>/수치.json` 으로 빼고, 통과한 프로토타입의 그 파일을
그대로 `Docs/Design/04-수치표.md` 의 재료로 쓴다. Unity 는 나중에 같은 JSON 을 읽는다.

## 7. 이 요청의 빈틈 · 보완할 점

사용자가 「내 피드백이 타당하지 않거나 보완할 점이 있으면 같이 조사해 달라」고 했다. 셋을 짚는다.

### ① 웹으로 답이 안 나오는 물음이 있다

웹 프로토타입은 **규칙·경제·선택**에는 강하지만 **손맛에는 답을 못 한다.**
「FPS 손전등 감각을 종이로 시험하는 것은 방법이 아니다 — 게임 필은 직접적인 시각·촉각 되먹임에 크게 기댄다」
([GMTK](https://gmtk.substack.com/p/whats-the-point-of-prototyping)).

| 물음 종류 | 어디서 | 왜 |
| --- | --- | --- |
| 합성 확률·가격·성장 시간·자원 고임 | **웹** | 숫자다 |
| 도감 채우는 맛, 「한 판 더」 | **웹** | 선택과 되먹임이다 |
| 조작감·타격감·이동 느낌 | **Unity 버릴 씬** | 프레임·물리·입력 지연이 답을 바꾼다 |
| 화면 연출·카메라·이펙트 타이밍 | **Unity 버릴 씬** | 엔진 기능 자체가 물음이다 |
| UI 배치가 헷갈리나 | 웹으로 절반, 나머지는 Unity | 웹은 배치만, 손끝 감각은 못 봄 |

**갈림 규칙 (제안)** : 4단계에서 물음을 적을 때 **「이 물음의 답이 숫자인가, 손끝인가」를 한 칸 더 적는다.**
손끝이면 그 프로토타입만 `ProjectMozziUnity` 밖의 버릴 씬으로 간다.
농장·합성 게임은 대부분 숫자 쪽이라 웹이 잘 맞는다 — 이번 요청은 **타당하다.** (의견)

### ② 여러 개를 한꺼번에 만들면 같은 방향으로 틀린다

이게 이번 계획의 가장 큰 실제 위험이다. LLM 은 **여러 번 따로 물어도 비슷한 데로 모인다**(모드 붕괴).
연구는 두 가지를 짚는다 — 한 판 안에서 **앞의 출력이 뒤를 붙든다(고착)**, 그리고 모델이 지식을
**하나의 분포로 뭉쳐** 사람 집단처럼 갈라지지 않는다.
— [LLM 아이디어 다양성의 장벽 (arXiv)](https://arxiv.org/pdf/2602.20408v1) ·
[다중 에이전트에서의 다양성 붕괴 (arXiv)](https://arxiv.org/pdf/2604.18005) ·
[LLM 이 창작 다양성을 균질화한다 (ScienceDirect)](https://www.sciencedirect.com/science/article/pii/S294988212500091X)

막는 법 (제안) :

1. **물음 축을 사용자가 먼저 다르게 못 박는다.** 프로토타입 3개면 「확률의 갈림 / 시간의 압박 / 선택의 폭」처럼
   **서로 다른 축**을 사용자가 4단계에서 적는다. AI 에게 「3개 만들어 줘」라고 열어 두면 셋이 닮는다.
2. **한 프로토타입 = 한 서브에이전트.** 같은 문맥에서 이어 만들면 앞 것이 뒤를 붙든다(고착).
   `CLAUDE.md` 의 병렬 규칙과도 맞는다 — 한 폴더는 한 갈래.
3. **다 만든 뒤 사용자가 「셋이 서로 다른가」를 먼저 본다.** 닮았으면 놀아 보기 전에 되돌린다. 시간이 아깝다.
4. 극단값을 일부러 넣는다. 하나는 **일부러 후하게**, 하나는 **일부러 짜게**. 가운데만 셋 만들면 배우는 게 없다.

### ③ 툴 만들기가 게임 만들기를 잡아먹는다

혼자 개발에서 흔한 실패다. 「2026년 최고의 혼자 개발 흐름은 **도구가 가장 많은 흐름이 아니다**」
([Ziva](https://ziva.sh/blogs/solo-game-development)). 「yak shaving」을 정면으로 다룬 글은 못 찾았지만,
도구를 쌓는 것이 역효과라는 이야기는 반복해서 나온다.

**막는 선 (제안)** :

- 6장 표의 **1·2번(템플릿 한 장 + 목록 페이지)까지가 이번에 만들 전부다.** 반나절을 넘기면 멈춘다.
- 3번(판정 표)은 **첫 검증을 한 번 겪고 나서** 만든다. 안 겪고 만들면 필요 없는 칸을 만든다.
- Go CLI 승격은 **같은 일을 세 번 손으로 한 뒤**에만.
- 판단 기준 한 줄 : **「이 툴이 없으면 이번 주말 검증을 못 하나?」** 아니면 안 만든다.

## 못 찾은 것

- 「프로토타입 갤러리 + 판정 기록」을 묶어 주는 **기성 도구·오픈소스 사례**. itch.io 말고는 안 나왔다.
- **「AI 가 한 파일에 몇 줄까지 안 틀리나」의 숫자 근거.** 방향(짧을수록 안전, 파일 여럿이 더 위험)만 확인했다.
- 라이브러리별 **정확한 KB 크기 표.** LittleJS 의 js13k 분기 7KB 말고는 숫자를 못 찾았다.
- CHI 2025 *All in One* 논문 **본문**(ACM 403). 요약 수준까지만 확인했다.
- 혼자 개발의 **「툴 만들기 함정」을 정면으로 다룬 글.** 간접 근거만 있다.
