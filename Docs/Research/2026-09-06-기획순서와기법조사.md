# 기획 순서와 기법 조사

2026-09-06 · 인터넷 조사 · 출처 20여 곳

## 한 줄 결론

게임 기획에도 코드의 디자인 패턴처럼 **정해진 순서(컨셉 → 기둥 → 코어 루프 → 종이·거친 프로토타입 → 검증 → 세로 조각 → 확장)** 와
**이름 붙은 구조·기법(MDA, 코어/메타 루프, 경제의 원천-배수구, 진행 곡선, 보상 표)** 이 있다.
혼자 만들 때는 **문서를 먼저 크게 쓰지 말고 한 장짜리로 시작해 프로토타입이 답을 줄 때마다 늘려 쓴다.**

## 이 프로젝트에 추천하는 순서

| 단계 | 무엇을 하나 | 산출물 | 대략 공수 |
| --- | --- | --- | --- |
| 1. 컨셉 한 줄 | 「누가 · 무엇을 하는 · 왜 재미있는 게임인가」를 한 문장으로 | `Docs/Design/00-컨셉.md` (반 쪽) | 1~2시간 |
| 2. 기둥 3개 | 이 게임이 지키는 느낌 3~4개. 하나를 바꾸면 다른 게임이 되는 것들 | 컨셉 문서 안 표 | 1시간 |
| 3. 코어 루프 | 플레이어가 1~3분 안에 반복하는 고리를 글 표로 그린다 | `Docs/Design/01-코어루프.md` | 2~3시간 |
| 4. 자원 흐름 | 무엇이 생기고(원천) 무엇이 없어지나(배수구), 사이에 무슨 변환이 있나 | 같은 문서 안 표 | 2~3시간 |
| 5. 종이·거친 프로토타입 | 그림 없이 네모와 숫자로만 코어 루프를 돌려 본다 | 버릴 씬 하나 | 1~3일 |
| 6. 검증 | 「5분 돌려서 또 하고 싶은가」만 본다. 아니면 3으로 되돌아간다 | 짧은 기록 한 편 | 반나절 |
| 7. 기능 자르기 | MoSCoW 로 Must/Should/Could/Won't 를 적는다 | `Docs/Design/02-기능목록.md` | 2시간 |
| 8. 세로 조각 | 하루치 플레이를 마무리 품질로 한 번 만든다 | 실제 씬 | 2~6주 |
| 9. 확장 | 콘텐츠 늘리기. 새 시스템은 여기서도 안 늘린다 | — | 나머지 전부 |

**3~6 을 도는 것이 기획의 본체다.** 1~2회 돌고 끝나는 일이 아니라 재미가 잡힐 때까지 돈다.

## 1. 기획 순서 (프로세스)

큰 흐름은 어디를 봐도 비슷하다 — **컨셉 → 프리프로덕션(프로토타입·세로 조각) → 프로덕션 → 다듬기 → 내보내기**.

| 용어 | 뜻 (한 줄) | 요령 |
| --- | --- | --- |
| 컨셉 | 「무슨 게임인가」 한 문단. 대상·장르·기분 | 남에게 20초 안에 말할 수 있어야 한다 |
| 기둥(design pillar) | 이 게임이 반드시 지키는 3~8개의 느낌. 하나를 갈아 끼우면 다른 게임이 됨 | **할 일이 아니라 느낌으로 쓴다.** 자를지 말지를 여기에 물어본다 |
| 코어 루프 | 플레이어가 계속 반복하는 짧은 행동 고리 | 「행동 → 결과 → 보상 → 다시 행동」 |
| 종이 프로토타입 | 종이·말·주사위로 규칙만 돌려 보기 | 만들기 전에 규칙이 틀렸는지 싸게 안다 |
| 프로토타입 | 빠르고 지저분하고 **버리는** 코드. 배우려고 만든다 | 예쁘게 만들지 않는다. 5분만 돌아가면 된다 |
| MVP | 코어 루프가 처음부터 끝까지 도는 **가장 작은 놀 수 있는 판** | 메타 진행·많은 콘텐츠·다듬은 UI 는 일부러 뺀다 |
| 세로 조각(vertical slice) | 게임의 한 조각을 **완성 품질로** 만든 것 (한 판·하루·한 지역) | 보통 1~3개월. 여기서 안 되면 본 제작으로 넘어가지 않는다 |
| 플레이테스트 | 남에게 쥐어 주고 **말없이 본다** | 「재미있었나」를 묻지 않는다. 「어디서 헷갈렸나/지루했나」를 묻는다 |

혼자 개발 기준 현실적인 조언 :

- **한 번에 하나만 배우는 프로토타입.** 한 판에서 답을 하나만 가져온다.
- **정해진 지점에서 결정을 한다.** 세로 조각이 재미없으면 그대로 본 제작에 들어가지 않는다 (Rami Ismail).
- **플레이테스트는 반복이다.** 고친 뒤 그 자리를 다시 시험해야 고쳐졌는지 안다.

## 2. 기획 문서의 구조

**결론 : 두꺼운 GDD 는 요즘 안 쓴다.** 큰 회사도 「살아 있는 문서(living doc)」 — 짧고 계속 고치는 위키 — 로 옮겨 갔다.
길고 딱딱한 문서는 관리가 안 되고 아무도 안 읽기 때문이다.

| 형태 | 크기 | 언제 쓰나 |
| --- | --- | --- |
| 한 장 기획(one-page) | 1쪽. 홍보 문구 · 기둥 · 코어 루프 · 제약 | **시작할 때. 우리 프로젝트는 여기서 출발한다** |
| 열 장 기획 | 10쪽 안팎. 시스템별 한 쪽씩 | 프로토타입이 재미를 증명한 뒤 |
| 전체 GDD | 수십 쪽 | 사람이 여럿이고 넘겨줄 것이 많을 때만 |

GDD 에 흔히 들어가는 칸 : 한 줄 컨셉 · 대상 플레이어 · 기둥 · 코어 루프 · 기능 목록 · 시스템 명세 · 진행과 콘텐츠 ·
그림/소리 방향 · UI · 기술 제약 · 규모와 위험 · 이정표.

혼자 만들 때 요령 : **글보다 그림·표로.** 그리고 「먼저 시험해 보고 살아남은 것만 문서에 적는다」 — 바뀔 것을 미리 적으면 헛수고다.

## 4. 기획 패턴 · 기법

### 4-1. 게임 디자인 패턴 (Björk & Holopainen)

코드의 GoF 패턴과 같은 자리다. 「자주 나오는 게임 부품」 200개 이상을 이름 붙여 모아 놓고,
자원 관리 · 사교 · 판(session) · 다시 하기 같은 11개 묶음으로 나눴다. 쓰임새도 GoF 와 같다 —
**말을 맞추고, 남의 게임을 뜯어 보고, 선택지를 떠올리는 데 쓴다.** 그대로 복사하는 카탈로그가 아니다.

출처 : <https://scispace.com/pdf/patterns-in-game-design-4gr3mrxuji.pdf> · <https://archive.org/details/patternsingamede0000bjor>

### 4-2. 경제 설계 — 원천과 배수구

| 낱말 | 뜻 | 예 |
| --- | --- | --- |
| 원천(source · faucet) | 자원이 **생기는** 곳 | 작물 수확, 퀘스트 보상 |
| 변환기(converter) | 자원을 다른 자원으로 **바꾸는** 곳 | 가공 기계, 합성 |
| 배수구(sink · drain) | 자원이 **없어지는** 곳 | 씨앗 사기, 수리, 업그레이드 |
| 앵커(anchor) | 그 자원을 원하는 진짜 **마음** | 꾸미기(자기표현), 자랑, 모으기 |

Lost Garden 의 「가치 사슬」 요령 :

- 사슬을 **팽팽하게** 유지한다 — 배수구가 원천보다 아주 조금 더 세야 자원이 고이지 않는다.
- **똑같은 성격의 원천 둘을 나란히 두지 않는다.** 플레이어가 효율 좋은 쪽만 쓰고 나머지 콘텐츠는 버려진다.
- **서로 다른 종류의 재료를 요구**하면 모든 콘텐츠를 골고루 쓰게 만들 수 있다.
- 원천·배수구를 「일정 / 선형 / 지수 / 적응형」으로 나눠 **세기를 짝지어** 본다.

들어오는 게 많으면 값이 싸지고 창고가 넘치며, 나가는 게 적으면 할 일이 없어진다 — 이 둘의 균형이 경제 설계의 전부다.

### 4-3. 진행 곡선 · 보상 표 · 난이도

| 기법 | 한 줄 뜻 | 코드 비유 |
| --- | --- | --- |
| 진행(progression) 곡선 | 비용·보상을 선형·지수 중 어느 곡선으로 올릴지 정하기 | 시간 복잡도 고르기 — 지수로 올리면 금방 벽에 부딪힌다 |
| 고정 비율 보상 | N번 하면 반드시 준다 | 확정 반환. 계획을 세우게 한다 |
| **변동 비율 보상** | 몇 번 만에 나올지 모른다. 가장 강하게 반복을 만든다 | 재시도 백오프의 무작위 값. **세게 쓰면 도박이 된다 — 절제** |
| 고정/변동 간격 보상 | 시간이 지나야 준다 (일일 보상 등) | 타이머·크론 |
| 난이도 곡선 | 실력이 늘어나는 만큼 난이도를 올려 몰입 통로 안에 둔다 | 부하 조절 |
| 튜토리얼 | **한 번에 하나씩**, 설명 화면이 아니라 놀면서 가르친다 | 점진적 노출(progressive disclosure) |

튜토리얼 요령 : 5초 안에 재미에 닿게 하고, 짧은 목표와 긴 목표를 일찍 보여 주고, 한 번에 한 기능만 꺼낸다.
설명이 따로 있어야 이해되는 조작은 조작이 잘못된 것이다.

### 4-4. 시스템 상호작용 표

시스템이 여럿이면 **가로·세로에 시스템을 놓고 칸마다 「A 가 B 에 무엇을 주나」를 적는** 표를 만든다.
빈 줄·빈 칸이 많은 시스템은 다른 것과 안 엮이는 곁가지라는 뜻이니 **자를 후보**다.
(이 표 자체를 다룬 정식 출처는 못 찾았다. Machinations 의 시스템 사고 글이 가장 가깝다.)

| | 밭 | 합성 기계 | 돈 |
| --- | --- | --- | --- |

## 5. 규모 잡기 · 자르기

**혼자 만들 때 가장 흔한 실패는 기능이 계속 늘어나는 것(scope creep)이다.**

| 기법 | 하는 법 |
| --- | --- |
| MoSCoW | 기능을 Must(없으면 게임이 아님) / Should(중요하나 미룰 수 있음) / Could(있으면 좋음) / Won't(이번엔 안 함) 로 나눈다 |
| 최소 재미 단위 | 「플레이어가 하는 가장 즐거운 한 가지」를 정하고 **그것부터 완성**한다. 곁가지는 그 뒤 |
| 시간 상자(timebox) | 기능마다 시간을 정해 두고, 시간이 다 되면 완성 여부와 상관없이 멈춘다 |
| 기둥으로 자르기 | 새 아이디어가 기둥 3개 중 하나를 더 세게 만들지 않으면 넣지 않는다 |
| 반복 계획 | 크게 한 번이 아니라 작은 판을 여러 번 — 매 판 끝에 놀 수 있는 상태를 만든다 |

자주 나오는 조언 : **잘 만든 기능 하나가 어설픈 열보다 낫다.** 콘텐츠를 늘리는 것보다 코어를 다듬는 것이 먼저다.

출처 : <https://www.wayline.io/blog/scope-creep-solo-indie-game-development> ·
<https://www.wayline.io/blog/essential-scope-rules-solo-game-dev> ·
<https://introvertedgames.com/game-development/managing-project-scope-a-survival-guide-for-indie-game-developers/> ·
<https://tonogameconsultants.com/scope-creep/>

## 6. 농장 · 경영 · 수집 · 합성 장르의 흔한 구조

### 코어 루프의 뼈대

이 갈래의 게임은 대개 **「자원 → 변환 → 더 나은 자원 → 더 빠른 변환」** 이라는 한 고리로 정리된다.

| 층 | 주기 | 하는 일 | 예 |
| --- | --- | --- | --- |
| 코어 | 몇 초~몇 분 | 심고 · 거두고 · 넣고 · 뽑는다 | 손맛 나는 반복 행동 |
| 하루 | 한 판(세션) | 오늘 할 일을 시간 안에 배치한다 | 하루가 끝나며 정산 |
| 메타 | 며칠~몇 주 | 시설 넓히기 · 도감 채우기 · 해금 | 「내일 또 켜는 이유」 |

### 하루 주기(day cycle)가 하는 일

시계가 있어야 **선택에 무게가 생긴다.** 「하루가 끝난다」는 사실이 물뿌리개 업그레이드를 값지게 만든다.
시간 · 체력 · 가방 칸이 이 갈래의 대표적인 **제약 세 가지**다. 제약이 없으면 최적 전략 하나만 남고 나머지는 안 쓰인다.

출처 : <https://altheragames.com/en/blog/simulation-game-economy-design> ·
<https://deliberategamedesign.com/resources-loop/> ·
<https://onewheelstudio.com/blog/2017/3/24/building-a-game-loop> ·
<https://medium.com/@yuriy.sivers/cycle-of-play-part-i-anatomy-of-the-game-loop-b500734849a5>

### 수집 · 합성(뽑기) 확률의 기본

우리 프로젝트는 필드에서 잡는 대신 **합성 기계로 뽑는 쪽**으로 정했으니 확률 규칙이 필요하다. 기본만 적는다.

| 개념 | 뜻 | 우리에게 |
| --- | --- | --- |
| 확률 표 | 등급마다 나올 확률을 정한 표 (예: 상 0.6% / 중 5% / 하 94%) | 등급을 3~4개보다 늘리지 않는다 |
| 소프트 천장(soft pity) | 몇 번 이상 꽝이면 **확률이 조금씩 올라간다** | 운 나쁜 사람의 체감을 지켜 준다 |
| 하드 천장(hard pity) | N번째는 **반드시** 좋은 것이 나온다 | 최악의 경우를 사람이 셀 수 있게 한다 |
| 기대 횟수 | 소프트 천장이 있으면 평균이 하드 천장보다 꽤 앞당겨진다 | 「몇 번이면 나오나」를 미리 계산해 둔다 |
| 중복 처리 | 이미 가진 것이 또 나올 때 다른 자원으로 바꿔 준다 | 중복이 그냥 꽝이면 금방 질린다 |

**돈을 받는 뽑기가 아니라면 확률을 짜게 잡을 이유가 없다.** 여기서 확률은 매출 장치가 아니라 「다음 것이 궁금하게 만드는 장치」다.

출처 : <https://mwm.ai/glossary/pity-system> ·
<https://gashapoint.com/gacha-games/what-is-gacha/> ·
<https://pulsegeek.com/articles/gacha-odds-and-pity-systems-explained-clearly/>
