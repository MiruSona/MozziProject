# 기획 루프 대시보드 조사 — 무엇으로 보고 무엇으로 조절하나

> 조사 대상 : 「기획·제작 루프의 지금 상태를 한 화면으로 보고 단계를 조절하는 웹 툴」
> 대상 틀 : `Docs/Guide/기획절차.md` 의 9단계 · 되돌아가는 고리 · 판(iteration) 규칙
> 출처는 문서 맨 뒤에 모았다. 못 찾은 것은 「못 찾은 것」 절에 적었다.

## 한 줄 결론

**기존 제품(HacknPlan·Notion·Obsidian)은 우리 규칙(저장소 안 파일이 정본, AI 가 읽고 고침)과 맞지 않는다.
「상태는 저장소 안 JSON 한 개, 조절은 CLI(`stage next`), 보기는 CLI 가 굽는 정적 HTML 한 장」이 맞다.**
웹에서 눌러 고치는 기능은 **처음엔 넣지 않는다** — CLI 로 충분하고, 넣는 순간 브라우저에서 파일에 쓰는
문제(File System Access API 가 Firefox·Safari 에 없다)를 떠안는다.

### 추천 구성

| 무엇 | 왜 | 대안 |
| --- | --- | --- |
| 상태 정본 = `Docs/Todo/기획상태.json` (git 안) | AI 가 읽고 고칠 수 있고 되돌리기가 git 으로 된다. 문서-as-code 의 기본 | YAML. 사람이 손으로 고치기 좋지만 파서가 더 필요 |
| 조절 = CLI `stage show/next/back/check` | 훅이 이미 CLI 다. 승인·기록이 git 커밋으로 남는다 | 웹 폼 → 로컬 서버 (뒤로 미룬다) |
| 보기 = `stage dash` 가 굽는 **정적 HTML 한 장** | 서버 없음. 파일 두 번 클릭이면 열린다. 사용자는 브라우저로 본다 | 로컬 서버 상주 — 우리 툴킷 원칙(상주 서버 없음)에 어긋난다 |
| 그리기 = 순수 CSS + Mermaid 코드펜스 | CDN 한 줄, AI 가 짜기 쉬움. 고리 있는 상태도는 Mermaid `stateDiagram-v2` | D3·Cytoscape — 우리 규모엔 과하다 |
| 화면 = **한 장 · 타일 7개 이하** | 「한 화면에 20개 위젯」이 대시보드 실패의 1순위 | 탭 여러 개 (나중에) |
| mem·EffortTool = **읽어서 얹기만** | 정본이 둘이 되면 반드시 어긋난다 | 대시보드가 따로 저장 — 금지 |

## 1. 무엇을 보여주나 — 보기만 / 조절

먼저 「한 화면에 다 넣지 말라」가 이 조사에서 가장 자주 나온 경고다. 사람이 한 번에 처리하는
덩어리는 7개 안팎인데 대시보드는 20개 위젯을 얹는다는 지적이 흔하다. 그래서 아래를 **「위 3칸 · 아래 4칸」
일곱 덩어리**로 줄였다. (출처 5·6)

| 보여줄 것 | 어디서 오나 | 보기만 / 조절 | 왜 |
| --- | --- | --- | --- |
| 지금 몇 단계인가 (1~9) | 상태 파일 | **조절** (`stage next`) | 단계 넘기기는 사용자만 한다 |
| 이번 판 물음 2~4개 + 판정 기준 | `01-코어루프.md` 맨 뒤 | 보기만 | 문서가 정본 |
| 프로토타입 묶음 상태 (만드는 중 / 확인 대기 / 통과 / 불통) | 상태 파일 | **조절** (`stage check <물음> pass|fail`) | 6단계에서 사용자가 적는다 |
| 되돌아간 횟수 (3~6 고리를 몇 판 돌았나) | 상태 파일에서 셈 | 보기만 | 3판이면 컨셉을 의심하라는 신호 |
| 기둥 3~4개 | `00-컨셉.md` | 보기만 | 새 아이디어를 거를 때 늘 눈에 있어야 한다 |
| MoSCoW 표 | `02-기능목록.md` | **조절** (칸 옮기기 — 다만 CLI 로 충분) | Won't 칸이 비면 경고 |
| 문서 뼈대 6개 중 쓴 것 | 파일 있나 없나 | 보기만 | 순서 훅이 보는 것과 같은 값 |
| 공수 예상/실제 | EffortTool | 보기만 | 눈금이 맞아 가는지 |
| 최근 결정 5건 | mem | 보기만 | 세션 훅이 넣는 것과 같은 값 |

**조절이 필요한 것은 셋뿐이다** — 단계 넘기기 · 프로토타입 통과/불통 · MoSCoW 칸.
나머지는 전부 문서·mem·EffortTool 이 정본이라 대시보드는 읽기만 한다.

## 2. 시각화 방법 — 무엇으로 그리나

| 그림 | 우리 어디에 쓰나 | ○△× | 근거 |
| --- | --- | --- | --- |
| **스테퍼(단계 표시줄)** | 9단계 가로 줄. 지난 단계·지금·앞으로 | ○ | 「지금 어디이고 다음이 무엇인지」를 보여주는 게 스테퍼의 목적 (출처 7) |
| **고리 있는 상태도** | 3→4→5→6→3 되돌아가는 고리 | ○ | 스테퍼는 곧게 가는 흐름 전제라 되돌아가는 화살표를 못 그린다. Mermaid `stateDiagram-v2` 로 따로 한 장 (출처 8) |
| **칸반 (열=상태, 카드=프로토타입)** | 이번 판 물음 2~4개 카드 | ○ | 「만드는 중 / 확인 대기 / 통과 / 불통」 네 열. 카드 4장이라 CSS 그리드로 충분 (출처 12) |
| **타임라인·간트** | 판 하나가 1~2주 | △ | 혼자 하는 1~2주짜리에 간트는 과하다. Mermaid gantt 는 「그리기만 하고 일정을 풀어주지 않는다」 (출처 9) |
| **지표 타일** | 되돌아간 횟수 · 공수 예상/실제 · 남은 물음 | ○ | 숫자 3~4개면 충분 |

**나쁜 예로 배운 것 셋** (출처 5·6·10)

- 「한 화면에 정보 종류가 너무 많다」가 가장 흔한 대시보드 실패다. 위젯 20개짜리 화면에서는
  「그래서 지금 어디냐」 같은 기본 물음조차 한눈에 안 잡힌다.
- 핵심은 노트북 한 화면 안에 넣고, 자세한 것은 링크로 문서에 넘긴다.
- 빈 자리는 낭비가 아니다. 지울 수 있는 장식은 다 지운다.

혼자 개발자용 「진행 상황 한 장」의 실제 사례는 Notion 템플릿 쪽에 많다 (출처 13·14). 공통점은
**로드맵 한 줄 + 지금 할 일 목록 + 막힌 것** 셋으로 끝난다는 것. 그 이상은 안 본다.

## 4. 저장소 안 데이터를 정본으로 하는 구조

원칙은 문서-as-code 의 것 그대로다 — **정본은 하나, 나머지는 그것에서 뽑는다.** 같은 값을 두 군데
적어 두면 반드시 어긋난다(문서 표류). (출처 10·11)

```
Docs/Todo/기획상태.json   ← 정본 (단계·판 번호·프로토타입 상태)
Docs/Design/*.md          ← 정본 (기둥·물음·판정 기준·MoSCoW)
mem / EffortTool          ← 정본 (결정·공수)
        │  읽기만
        ▼
stage dash → Docs/Todo/대시보드.html   ← 굽는 것. 지워도 다시 만들면 된다
```

### 「조절」을 어떻게 하나 — 두 방식

| 방식 | 어떻게 | 장점 | 단점 | 판정 |
| --- | --- | --- | --- | --- |
| **(가) 웹에서 고쳐 파일에 쓰기** | File System Access API 로 브라우저가 직접 JSON 을 쓴다 | 브라우저만으로 끝 | **Chrome·Edge 계열만 된다. Firefox 는 「해롭다」고 표명했고 Safari·모바일도 안 된다.** HTTPS/localhost 필요, 사용자 클릭이 있어야 열린다. 대안인 `download` 는 덮어쓰기가 안 된다 | 지금은 × |
| **(가-2) 작은 로컬 서버** | `stage serve` 로 localhost 를 띄우고 폼으로 고친다 | 브라우저 제약 없음 | 상주 프로세스가 생긴다. 우리 툴킷은 「상주 서버·MCP 없음」이 원칙 | 나중에 △ |
| **(나) CLI 로 고치고 다시 굽기** | `stage next` → 상태 파일 고침 → HTML 다시 구움 | 훅·AI·git 과 그대로 맞물린다. 승인 절차가 이미 있다 | 사용자가 명령을 쳐야 한다 (또는 AI 에게 말하면 된다) | **○ 이것으로 시작** |

(가)의 브라우저 제약은 출처 25·26·27 을 근거로 한다.

**mem·EffortTool 얹기** — 둘 다 Go CLI 라 `mem search --json` 류 출력이나 `effort list` 출력을
`stage dash` 가 불러다 표로 넣으면 된다. **대시보드는 저장하지 않는다.** 굽는 시점의 사진일 뿐이다.

## 5. 그리기 라이브러리

| 후보 | 무엇에 | 크기·설치 | AI 가 짜기 | 판정 |
| --- | --- | --- | --- | --- |
| **순수 CSS 그리드** | 스테퍼 · 칸반 4열 · 지표 타일 | 0 (인라인 CSS) | 아주 쉬움. `grid-auto-flow: column` 한 줄로 칸반 열이 선다 | **○ 기본** |
| **Mermaid** | 되돌아가는 고리 상태도(`stateDiagram-v2`), 필요하면 `kanban`·`gantt` | CDN 한 줄 | 쉬움. 텍스트라 diff 가 읽힌다 | **○ 상태도용** |
| D3 | 자유 도형 | 큼, 배우기 어려움 | 어려움 | × |
| Cytoscape.js | 노드 많은 그래프·경로 찾기 | 중간 | 중간 | × (노드 9개엔 과하다) |
| vis.js (vis-network) | 물리 배치 대화형 네트워크 | 중간 | 쉬운 편 | × |

- Mermaid 는 11.4 에서 `kanban` 을 넣었고 열·카드·우선순위·티켓 링크까지 된다. 다만 **칸반은 그림이라
  드래그가 안 된다.** 우리 카드는 4장뿐이라 CSS 로 그리는 편이 낫다. (출처 8·28)
- Mermaid `gantt` 는 「쓴 대로 그릴 뿐 일정을 풀지 않는다」는 한계가 명시돼 있다. (출처 9)

### DiagramTool 과 겹치나

**거의 안 겹친다.** DiagramTool 은 마크다운 **문서 안 코드펜스**를 검사하고 그리는 도구다
(`tilemap`·`timeline`·`chain`). 상태도(`mermaid` 펜스)는 **도구 없이 규칙만** 있다고 README 에 적혀 있다.
대시보드는 문서가 아니라 **상태 파일**을 읽어 HTML 한 장을 굽는 것이라 입력도 출력도 다르다.
겹치는 것은 「HTML 로 굽는다」는 것 하나뿐이니, **CSS 만 DiagramTool 의 `wireframe.css` 와 결이 맞추면 된다.**

## 6. 만들까 살까 — 만든다 (최소로)

산 것으로 대신할 수 없다는 것은 3절에서 봤다. 다만 **작게 만든다.**

### 최소 구성

| 부품 | 무엇 | 크기 눈금 |
| --- | --- | --- |
| `Docs/Todo/기획상태.json` | 단계(1~9) · 판 번호 · 되돌아간 기록 · 프로토타입 배열(물음/상태/기준 링크) | 30줄 |
| `stage show` | 지금 단계·판·물음 상태를 글로 | 터미널 출력 |
| `stage next` / `stage back <단계> --why "…"` | 단계 옮기기. **되돌아간 기록을 남긴다** | 되돌아간 횟수는 여기서 셈 |
| `stage check <물음id> pass|fail --note "…"` | 6단계 통과/불통 적기 | mem history 도 같이 권한다 |
| `stage lint` | 훅이 부르는 모양 검사 (기둥 3~4개인가 · Won't 비었나 · 문서 순서) | 기획절차.md 의 훅 표 그대로 |
| `stage dash` | 정적 HTML 한 장 굽기 (`Docs/Todo/대시보드.html`, gitignore) | 템플릿 1개 |

훅 연결은 `Docs/Guide/기획절차.md` 의 표를 그대로 쓴다 — `SessionStart` 에 `stage show`,
`PreToolUse` 에 `stage lint`, `Stop` 에 판 끝 세 가지 확인.

### 화면 배치 (한 장, 위에서 아래로)

| 자리 | 무엇 | 어떻게 그리나 |
| --- | --- | --- |
| 맨 위 띠 | **9단계 스테퍼** — 지난 단계 채움, 지금 단계 강조, 앞은 흐리게. 옆에 「판 3회차」 | CSS 그리드 9칸 |
| 그 아래 한 줄 | 지표 타일 3개 — 되돌아간 횟수 / 이번 판 물음 4개 중 통과 2 / 공수 예상 대비 실제 | CSS 카드 3장 |
| 왼쪽 넓은 칸 | **프로토타입 칸반** — 열 4개(만드는 중·확인 대기·통과·불통), 카드에 물음 한 줄 + 판정 기준 개수 | CSS 그리드 4열 |
| 오른쪽 좁은 칸 | **기둥 3~4개** 상자 (늘 보이게) + 문서 뼈대 6줄 체크 표시 | 목록 |

**타일 세는 법 : 위 6덩어리.** 일곱을 넘기지 않는다.

## 7. 이 요청의 빈틈 · 보완할 점

사용자 요청(「루프를 한눈에 보고 조절하는 웹 툴」)에 대해 **되짚어야 할 것 넷**이다.

### ① 게임 대신 툴을 만드는 함정

**의견이다** — 「인디 개발자가 게임 대신 엔진·툴을 만들다 끝난다」는 현상을 정면으로 다룬 자료는
이번 검색에서 못 찾았다. 가장 가까운 언급은 「대부분의 인디에게 필요한 건 엔진 하나와 생성기 두셋인데
구독 열 개를 사는 것이 함정」이라는 정도다 (출처 29). 그래도 이 프로젝트는 **아직 1단계 컨셉도 안 끝났는데
툴 조사가 세 건 동시에 도는 상태**라 위험이 실제로 있다.

막는 선을 숫자로 못 박자고 제안한다.

| 선 | 값 |
| --- | --- |
| 만드는 데 쓰는 시간 | **반나절(4시간) 안**. 넘으면 만들다 말고 `진행상황.md` 로 돌아간다 |
| 화면 | **한 장.** 탭·라우팅·로그인 없음 |
| 코드 | 상태 파일 읽기 + 템플릿 채우기. **JS 로직 없음**(Mermaid 렌더 빼고) |
| 만드는 때 | **기획절차 틀이 확정된 뒤.** 지금은 조사만 |

### ② 대시보드가 또 하나의 정본이 되는 위험

가장 현실적인 위험이다. `Docs/Todo/진행상황.md` 에도 「지금 할 일」이 있고 상태 파일에도 단계가 있으면
두 곳이 어긋난다. 같은 내용을 여러 문서에 복사해 두는 것이 문서 표류의 원인이라는 지적 그대로다 (출처 10·11).

막는 구조 셋을 제안한다.

1. **겹치는 값을 애초에 안 만든다.** 상태 파일에는 `진행상황.md` 에 없는 것(단계 번호·판 번호·프로토타입
   통과/불통)만 넣는다. 기둥·물음·MoSCoW 는 문서에서 **읽어 오기만** 한다.
2. **`진행상황.md` 의 맨 위 한 줄을 `stage` 가 고친다.** 「지금 4단계 · 3판째」 한 줄만 자동으로 덮는다.
   사람이 손으로 안 고치니 어긋날 자리가 없다.
3. **구운 HTML 은 git 에 안 넣는다** (`.gitignore`). 남아 있으면 낡은 사진이 정본처럼 보인다.
   화면 아래에 「언제 구웠나」를 반드시 찍는다.

### ③ 「조절」이 정말 필요한가

**대부분 필요 없다.** 나누면 이렇다.

| 조절 | CLI 로 충분한가 | 왜 |
| --- | --- | --- |
| 단계 넘기기 | **CLI 로 충분** | 한 판에 한두 번뿐이다. 게다가 되돌아간 까닭을 글로 적어야 해서 어차피 타자를 친다 |
| 프로토타입 통과/불통 적기 | **웹이 나을 수 있다** | 6단계는 사용자가 게임을 켜 놓고 몰아서 본다. 그때 터미널로 돌아가는 것이 흐름을 끊는다. 다만 4개짜리라 종이·메모로도 된다 |
| MoSCoW 칸 옮기기 | **CLI 도 과하다** | 문서를 직접 고치거나 AI 에게 말하면 된다 |

따라서 **1판은 읽기 전용으로 만들고**, 6단계를 실제로 한 번 돌려 본 뒤 「통과/불통 적기」만 조절 기능으로
넣을지 정하자고 제안한다. 그때는 로컬 서버(가-2)가 브라우저 API(가)보다 낫다 — 파일 접근 API 가
Firefox·Safari 에 없어서다 (출처 25·26).

### ④ 다른 조사 둘과 합칠 수 있나

**합칠 수 있고, 합치는 게 낫다는 의견이다.** 지금 도는 조사 셋의 뼈대가 같다.

| 조사 | 정본 | 굽는 것 |
| --- | --- | --- |
| 기획 루프 대시보드 (이 문서) | 상태 JSON + 기획 문서 | 상태 한 장 |
| 웹 프로토타입 툴 | `Prototypes/` 폴더 | 프로토타입 목록·실행 페이지 |
| 수치·밸런스 대시보드 | 수치 데이터 파일 | 곡선 그림 |

셋 다 **「저장소 안 파일 → 정적 HTML」** 이고, 셋 다 Go CLI + `embed` 템플릿으로 끝난다.
툴 하나(가칭 `stage`)에 **페이지 셋**(`stage dash` · `stage dash --protos` · `stage dash --numbers`)으로
두면 CSS·템플릿·굽는 코드를 한 번만 만든다. 다만 **판단은 다른 두 조사 결과를 보고 하는 게 맞다** —
수치 대시보드가 대화형(슬라이더로 곡선 바꾸기)을 요구하면 그것만 따로 떼야 할 수 있다.

## 못 찾은 것

- **「기획 단계 자체」를 보여주는 대시보드 제품** — 칸반·GDD 툴은 많은데, 「지금 컨셉 단계인가 검증
  단계인가」를 상태로 다루는 제품은 못 찾았다. 그래서 만들자는 결론이 됐다.
- **혼자 개발에서 툴 만들기에 빠지는 실패 사례를 다룬 글** — 정면으로 다룬 자료를 못 찾았다. 7절 ①은 의견이다.
- **Cytoscape·vis.js·D3 의 실제 CDN 파일 크기 비교 숫자** — 비교 글은 있었으나 KB 숫자를 밝힌 자료를 못 찾았다.
- **Mermaid `kanban` 이 정확히 어느 판에 들어갔는지** — 11.4 라는 블로그 언급은 봤으나 공식 문법 문서에는
  판 번호가 안 적혀 있다.
- **HacknPlan 을 파일로 내보내 git 에 넣는 방법** — 가능한지 확인 못 했다.
