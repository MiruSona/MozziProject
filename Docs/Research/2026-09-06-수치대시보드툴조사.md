# 수치·밸런스 데이터와 웹 대시보드 툴 조사

조사일 : 2026-09-06
물음 : 「게임 수치·밸런스를 자체 데이터 파일로 두고, 웹 대시보드에서 보고 고치는 방법과 툴」
전제 : 스프레드시트는 안 쓴다 (사용자 결정). 상주 서버·MCP 없이 CLI + 정적 HTML 을 선호.
표기 : `[확인]` 원문을 직접 봄 · `[전언]` 검색 요약만 봄 · `[의견]` 근거 있는 내 판단

## 한 줄 결론

**데이터는 `Data/*.json` 한 벌로 두고, 「보기」는 CLI 가 굽는 정적 HTML 대시보드,
「고치기」는 AI 가 JSON 을 직접 편집한다.** 기존 툴 중 우리 규칙에 딱 맞는 것은 없고,
직접 만들 때도 최소 구성이면 작다 (2~3일 눈금).

### 추천 구성

| 무엇 | 왜 | 대안 |
| --- | --- | --- |
| **데이터 형식 : JSON (파일 여러 개, 종류별로 쪼갬)** | git diff 가 읽힌다 · AI 가 가장 잘 고친다 · Unity 가 Newtonsoft 로 바로 읽는다 | 사람이 손으로 자주 고칠 파일만 TOML. CSV·SQLite 는 비추 |
| **스키마 : JSON Schema + `balance check` 로 검사** | 오타·빠진 칸을 커밋 전에 잡는다. 스키마 자체가 「이 표에 무슨 칸이 있나」 설명서가 된다 | 없이 가다가 데이터가 커지면 넣기 |
| **곡선 : 값을 다 적지 말고 「식 + 검산용 몇 점」** | 레벨 100까지 손으로 적으면 못 읽는다 | 짧은 곡선(10단계 이하)은 그냥 값을 다 적는다 |
| **보기 : `balance dash` 가 자기완결 HTML 한 장을 굽는다** | 서버가 필요 없다. 더블클릭하면 열린다. AI 가 짜기 쉽다 | 로컬 미니 서버 (고치기까지 하려면 필요) |
| **그래프 : Chart.js (CDN 한 줄)** | 50~60KB · 예제가 많아 AI 가 실수 없이 짠다 | 점이 아주 많으면 uPlot, 통계 그림이면 Vega-Lite |
| **고치기 : 웹에서 안 한다. AI 가 JSON 을 직접 고친다** | 브라우저에서 파일 저장은 제약이 많고, 우리는 「사람이 말하면 AI 가 고친다」 구조다 | 나중에 정말 필요하면 로컬 서버 + 표 편집기 |
| **검증 : `balance sim` 으로 N일 자동 플레이** | 표만 봐서는 안 보이는 「고이는 자원 · 막히는 구간」이 여기서 나온다 | 손으로 계산 |
| **만들까 살까 : 만든다 (BalanceTool)** | 기존 툴은 전부 「사람이 GUI 로 고친다」 전제라 AI 가 못 쓴다 | Game Balance Editor (Windows, 원하는 만큼 내기) 를 먼저 써 보고 판단 |

## 1. 데이터 형식 — 무엇에 담나

### 비교

| 형식 | 무엇 | 장점 | 단점 | 우리에게 |
| --- | --- | --- | --- | --- |
| **JSON** | 가장 흔한 데이터 형식 | 줄 단위로 쪼개 두면 git diff·merge 가 된다 · AI 가 가장 잘 다룬다 · Unity 가 읽는 길이 확실하다 · JSON Schema 로 검사된다 | 주석을 못 단다 · 뒷 쉼표 하나로 깨진다 · 표 데이터는 세로로 길어진다 | **○ 기본** |
| **TOML** | 사람이 손으로 쓰는 설정용 | 주석이 된다 · 타입이 또렷하다 (`3.14` 는 실수, `"3.14"` 는 글자) · 얕은 설정에 깔끔 | 깊게 겹치면 지저분 · Unity 쪽 읽기 라이브러리를 따로 넣어야 함 | △ 사람이 자주 손댈 설정 몇 개만 |
| **YAML** | 들여쓰기로 구조를 잡는 형식 | 사람이 읽기 좋다 · 주석 된다 | **함정이 많다** — 탭 하나에 깨지고, `yes` 가 참으로, 국가코드 `NO` 가 거짓으로 읽힌다 | × |
| **CSV** | 표 한 장 | 표 데이터에 가장 짧다 · diff 가 줄 단위라 깔끔 | 칸 이름이 맨 윗줄에만 있어 값만 봐서는 뭔지 모른다 · 겹친 구조를 못 담는다 · 타입이 없다 | △ 표만 있는 것 (작물 50종) 은 후보 |
| **SQLite** | 파일 하나짜리 데이터베이스 | 질의가 된다 · 큰 데이터에 강하다 | **binary 라 git diff 가 안 된다** — 전용 diff/merge 드라이버를 따로 붙여야 한다 · AI 가 직접 못 고친다 | × |

> 근거 : 형식별 성질 비교 [전언](https://www.anbowell.com/blog/an-in-depth-comparison-of-json-yaml-and-toml/) ·
> SQLite 를 git 에 넣으려면 전용 드라이버가 필요하다 [전언](https://github.com/cannadayr/git-sqlite) ·
> SQLite/DuckDB 를 CSV 폴더로 풀어야 diff·버전관리가 된다는 도구가 따로 있을 정도다 [전언](https://github.com/jeff-gorelick/csvdb) ·
> 밸런스 데이터를 「폴더 하나 가득한 평범한 JSON 파일」로 두면 코드처럼 diff·merge 된다 [확인](https://muchopincho.itch.io/game-balance-editor)

### 표 데이터와 곡선을 어떻게 담나

**표 (작물·찹쌀이 50종)** — 종류마다 파일 하나로 쪼개지 말고, **한 종류 = 한 파일**로 묶는다.
`crops.json` 안에 배열로 50줄. 한 줄이 한 종이면 diff 에서 「무엇이 바뀌었나」가 한눈에 보인다.

**곡선 (레벨별 비용 · 성장 시간)** — 값을 100개 적지 말고 **식과 검산용 몇 점**을 적는다.

```json
{
  "id": "upgrade_cost",
  "formula": "base * pow(growth, level - 1)",
  "base": 100, "growth": 1.35, "maxLevel": 40,
  "checkpoints": { "1": 100, "10": 1806, "40": 12000000 }
}
```

`checkpoints` 는 「식이 맞나」를 `balance check` 가 자동으로 대 보는 자리다.
식을 고쳤는데 검산점이 안 맞으면 바로 잡힌다. [의견]

> 곡선을 눈으로 만지는 기능(수식 + 키프레임 곡선 만들기)을 갖춘 상용 툴이 이미 있다 —
> Game Balance Editor 의 「progression curve builder」 [확인](https://muchopincho.itch.io/game-balance-editor)

### 스키마 검사

JSON Schema 로 「이 파일에 무슨 칸이 있고 어떤 타입인가」를 적어 두고 CLI 로 검사한다.
구조 오류·타입 어긋남·빠진 필수 칸을 커밋 전에 잡는다.
대표 도구는 **Ajv CLI** (Node, `ajv validate -s schema.json -d data.json`) [전언](https://ajv.js.org/packages/ajv-cli.html),
Rust 쪽은 `jsonschema-cli` [전언](https://crates.io/crates/jsonschema-cli).
우리 툴이 Go 라면 Go 용 JSON Schema 라이브러리를 안에 품는 쪽이 낫다. [의견]

### Unity 에서 읽기

| 길 | 성질 |
| --- | --- |
| `JsonUtility` (내장) | **`Dictionary` 를 못 담는다.** public 필드만 된다. 프로퍼티·비공개 필드 안 된다 [전언](https://medium.com/@rohan5210work/a-unity-developers-guide-to-mastering-json-from-jsonutility-to-newtonsoft-102de5ef9c11) |
| **Newtonsoft Json.NET** (`com.unity.nuget.newtonsoft-json`, 공식 패키지) | Dictionary·프로퍼티·상속 다 된다. **이걸 쓴다** [확인](https://docs.unity3d.com/Packages/com.unity.nuget.newtonsoft-json@3.0/manual/index.html) |
| ScriptableObject 로 굽기 | JSON → SO 에셋으로 변환해 두면 Unity 안에서 참조가 편하다. 다만 SO 는 **수치 통으로만** 쓴다는 우리 규칙 안에서 |

> 참고 : ScriptableObject 만으로 가면 「데이터를 Unity 안에서만 고칠 수 있고, 아이템 100개면 에셋 100개가
> 생겨 감당이 안 된다」는 불만이 실제로 있다. 그래서 외부 JSON DB 로 옮긴 사례가 있다
> [확인](https://www.gamedeveloper.com/programming/beyond-scriptable-objects-unity-data-management-with-castledb).
> 우리 규칙(「AI 는 인스펙터를 못 본다」)과 같은 방향의 근거다.

## 3. 웹 대시보드 방식

### 뼈대

```
Data/*.json  ──(CLI: balance dash)──▶  Dashboard/index.html  ──(더블클릭)──▶  브라우저
```

CLI 가 **JSON 을 HTML 안에 그대로 박아 넣고** 그림 그리는 코드를 붙여 한 장으로 굽는다.
서버가 없어도 되고, 파일 하나라 어디로든 옮길 수 있다.
이 방식은 시험 도구들이 이미 널리 쓴다 — 결과 JSON 을 자기완결 HTML 한 장으로 바꿔 준다
[전언](https://www.artillery.io/docs/reference/cli/report) · [전언](https://docs.usebruno.com/bru-cli/builtInReporters).
데이터를 `<script type="application/json">` 에 그대로 넣고 JS 로 꺼내 쓰는 것이 흔한 수법이다.

### 그래프 라이브러리

| 이름 | 크기 | 성질 | 우리에게 |
| --- | --- | --- | --- |
| **Chart.js** | 50~60KB | 선·막대·원 기본기. 예제가 산더미라 AI 가 실수 없이 짠다. CDN 한 줄 | **○ 기본** |
| **uPlot** | 약 50KB | **가장 빠르고 작다.** 16만 점을 25ms 에 그린다. 3600점 60fps 에서 CPU 10%·RAM 12MB (Chart.js 는 40%·77MB) | ○ 시뮬레이션 결과처럼 점이 아주 많을 때 |
| **Vega-Lite** | 200~300KB | 「무엇을 어디에 매핑」식 문법. 짧은 선언으로 통계 그림이 나온다 | △ 배우면 강하지만 AI 가 틀리기도 |
| **Observable Plot** | (숫자 확인 못 함) | Vega-Lite 와 같은 문법 계열 | △ |
| **Plotly.js** | **1MB 넘음** | 확대·이동·툴팁이 공짜로 딸려 온다. WebGL | × 우리 규모에 과하다 |

> 근거 : Chart.js 50~60KB, Plotly 1MB 초과, Vega-Lite 200~300KB [전언](https://lalatenduswain.medium.com/the-complete-guide-to-javascript-charting-libraries-in-2026-choosing-the-right-visualization-tool-dac9aeb15f60) ·
> uPlot 성능 실측 [확인](https://github.com/leeoniya/uPlot) · [사용기](https://cprimozic.net/notes/posts/my-thoughts-on-the-uplot-charting-library/) ·
> 라이브러리 비교표 [전언](https://tanstack.com/charts/latest/docs/comparison) · [npmtrends](https://npmtrends.com/chart.js-vs-echarts-vs-plotly.js-vs-vega-lite)

### 「고치기」까지 하려면 무엇이 필요한가

**브라우저에서 로컬 파일에 바로 저장하는 것은 제약이 크다.**

- File System Access API 로 「열기 → 고치기 → 같은 파일에 저장」이 되긴 한다 [확인](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access).
- 그런데 **Firefox 는 파일 고르기(picker)를 안 만들겠다고 공표**했고, **Safari 는 picker 없이 격리 저장소만** 준다.
  아이폰·아이패드는 어느 버전에서도 안 된다. 안드로이드 브라우저들도 picker 를 건너뛴다 [전언](https://www.testmuai.com/learning-hub/file-system-access-api-browser-support/).
- **HTTPS 나 localhost 에서만 돈다.** `file://` 로 연 페이지에서는 `showOpenFilePicker` 가 아예 없다.

즉 **`file://` 로 여는 정적 HTML 한 장에서는 「고치고 저장」이 안 된다.** 세 갈래뿐이다.

| 갈래 | 무엇 | 장점 | 단점 |
| --- | --- | --- | --- |
| **가. 보기만 웹, 고치기는 AI** | 대시보드는 읽기 전용. 사용자는 보고 「밀 값 12로」라고 말하고 AI 가 JSON 을 고친 뒤 다시 굽는다 | **공수가 가장 작다** · 고친 이유가 대화·mem 에 남는다 · git 이력이 깨끗하다 | 사용자가 직접 슥슥 못 만진다 · AI 를 거쳐야 해 왕복이 있다 |
| 나. 로컬 미니 서버 | `balance serve` 가 localhost 를 띄우고, 표 편집기(Tabulator·Jspreadsheet)로 고치면 서버가 파일에 쓴다 | 손맛이 스프레드시트에 가깝다 | 툴이 두 배로 커진다 · 켜 두어야 한다 · 편집 UI·검증·되돌리기를 다 만들어야 한다 |
| 다. 브라우저에서 내려받기 | 고친 뒤 JSON 을 다운로드 → 사람이 덮어쓰기 | 서버 없이 됨 | 덮어쓰기를 사람이 손으로 해야 해 실수가 난다 |

표 편집 UI 라이브러리 (나 갈래를 갈 때) : **Tabulator** (무료·오픈소스, 읽기 위주 표에 좋다) [확인](https://www.tabulator.info/) ·
**Jspreadsheet CE** (MIT, 상업 이용 무료, 엑셀식 조작·수식) [전언](https://jspreadsheet.com/frameworks/javascript-table) ·
**Handsontable** (비상업만 무료, **상업 이용은 유료**) [전언](https://handsontable.com/).
스키마로 폼을 자동 생성하는 쪽은 react-jsonschema-form·json-edit-react 계열 [전언](https://npm-compare.com/jsoneditor,jsoneditor-react,react-json-editor-ajrm,react-json-view,react-jsonschema-form).

**권고 [의견] : 「가」로 시작한다.** 「나」는 필요해지면 그때 붙인다 — 데이터 폴더와 스키마가 같으므로 나중에 얹어도 버리는 게 없다.

## 4. 밸런스 검증 기능

대시보드가 그림만 그리면 반쪽이다. **데이터를 읽어 자동으로 돌려 보고, 규칙 위반을 잡아 주는 것**이 본체다.

| 검사 | 무엇을 보나 | 근거 |
| --- | --- | --- |
| **N일 자동 플레이 (시뮬레이션)** | 정해진 방식으로 노는 가상 플레이어를 30일 돌려 자원 곡선을 그린다. 「느긋한 사람 · 보통 · 열심히」 셋을 따로 돌린다 | 평균 하나만 보지 말고 여러 성향으로 30일 돌려 보라는 권고 [전언](https://dev.to/hiroshi_takamura_c851fe71/game-economy-balancing-how-to-tune-rewards-costs-and-progression-2ale) |
| **원천 ÷ 배수구 균형** | 버는 속도와 쓰는 속도를 자원별로 재서 나눈다. 1 보다 크게 오래 가면 자원이 고인다 | 모든 배수구를 「무엇이 들어가나」로 정의하고, 짝지을 원천이 없는 배수구는 굶기거나 부풀릴 뿐이다 [전언](https://dev.to/sam_novak_574b07811e18495/idle-game-economy-design-what-your-currency-sinks-actually-eat-1non) |
| **곡선이 겹치나** | 업그레이드 비용 곡선과 하루 수입 곡선을 **한 그림에** 그려서, 비용이 수입 위로 솟는 「절벽」을 찾는다 | 위와 같은 글 [전언] |
| **뽑기 기대 횟수·천장** | 확률 p 면 기대 뽑기 수는 1/p (기하분포). 천장이 있으면 그 앞에서 잘린다. 소프트 천장이면 구간별로 계산 | 0.6% → 약 167회, 하드 천장 90회 같은 계산 [전언](https://miniwebtool.com/gacha-pity-calculator/) · [전언](https://calwhat.com/en/Cal/GachaExpectedValue) |
| **몬테카를로** | 확률이 섞인 것(합성 갈림·변종)은 평균만 보면 속는다. 여러 번 돌려 **분포**를 본다 | 평균은 오해를 부르니 분포를 보라 [전언](https://machinations.io/articles/what-are-game-simulations-and-why-should-you-care) |
| **경고 규칙** | ① 배수구 없는 자원 ② 30일 동안 한 번도 안 쓰인 원천 ③ 성격이 같은데 효율만 다른 원천 둘 (약한 쪽이 죽는다) ④ 검산점과 식이 어긋남 | 우리 `기획절차.md` 3단계 함정과 같은 내용 |

이런 검사를 **CLI 로 돌리고 결과를 대시보드에 얹는** 완성품은 못 찾았다.
Machinations 는 웹 GUI 안에서 다 하고, 나머지는 스프레드시트 + 파이썬 스크립트로 각자 만들어 쓴다 [전언].
**그래서 이 자리가 우리 툴이 값을 하는 곳이다.** [의견]

## 5. DiagramTool 과의 관계

**겹치지 않는다. 나눠 둔다.** [의견]

| | DiagramTool | 수치 대시보드 |
| --- | --- | --- |
| 무엇을 다루나 | **문서 안에 손으로 적은 도면** (타일맵·페이싱·생산 사슬) | **게임이 실제로 읽는 데이터 파일** |
| 언제 쓰나 | 문서를 쓸 때 | 수치를 고칠 때마다 |
| 결과 | 문서에 박히는 그림 + 검사 결과 | 따로 여는 HTML 한 장 |
| 고치면 게임이 바뀌나 | 아니다 (설명용) | **그렇다** |

DiagramTool 은 Node.js 로 도면을 검사하고 HTML 을 뽑는다 ([README](Tools/DiagramTool/README.md) 확인함).
「마크다운을 읽어 HTML 을 뽑는다」는 겉모습은 닮았지만, **입력이 문서냐 데이터냐**가 다르다.
합치면 프로필·검사 규칙이 뒤섞여 둘 다 어려워진다.

다만 **`lint.js` 의 생산 사슬(chain) 검사는 겹칠 소지가 있다.**
지금은 문서 안 표를 검사하는 것이니 그대로 두고, 수치 쪽은 데이터 파일을 본다. 겹치면 그때 정리한다.

## 6. 만들까 살까

**만든다.** 이유는 셋이다. [의견]

1. 기존 툴은 전부 「사람이 GUI 로 고친다」 전제다. 우리는 **AI 가 파일을 고치고 사람은 본다**가 기본이다.
2. 우리가 진짜 원하는 것(자동 검증 + 웹 대시보드)을 가진 완성품이 없다.
3. 최소 구성이면 작다. 데이터는 JSON, 그림은 CDN 한 줄, 굽는 것은 문자열 이어붙이기다.

**단, 먼저 Game Balance Editor 를 한 번 써 본다** (원하는 만큼 내기, Windows).
곡선 만들기·계산 칸·기대 곡선 대조가 우리가 만들려는 것과 겹친다.
써 보고 「JSON 폴더 구조가 우리 데이터 폴더로 그대로 쓸 만한가」만 확인하면 설계 시간이 줄어든다.

### 우리 툴킷에 만든다면 (BalanceTool 최소 구성)

```
Tools/BalanceTool/            ← Go 단일 실행 파일, 서브모듈
  balance.exe
  Docs/…

MozziProject/
  Data/                       ← 게임 저장소 쪽. 진실은 여기 하나뿐
    schema/
      crops.schema.json
      curves.schema.json
      gacha.schema.json
    crops.json                ← 표 : 작물·찹쌀이 목록
    curves.json               ← 곡선 : 식 + 검산점
    economy.json              ← 원천·배수구 정의 (무엇이 무엇을 낳고 먹나)
    gacha.json                ← 합성 갈림 확률·천장
    sim.json                  ← 시뮬레이션 설정 (며칠 · 어떤 성향 · 몇 번)
  Dashboard/index.html        ← 구워지는 결과물. git 에 안 넣는다
```

| 명령 | 하는 일 | 눈금 |
| --- | --- | --- |
| `balance check` | 스키마 검사 + 검산점 대조 + 경고 규칙(배수구 없는 자원 등). 잡히면 exit 1 | 0.5일 |
| `balance sim` | N일 자동 플레이. 성향별·몬테카를로. 결과를 `sim-result.json` 으로 | 1일 |
| `balance dash` | 위 결과와 데이터를 박아 넣어 **자기완결 HTML 한 장**을 굽는다 (Chart.js CDN) | 0.5일 |
| `balance bake` | JSON → Unity 로. `Assets/_Project/Data/` 에 JSON 복사 (+ 필요하면 C# 클래스 생성) | 0.5일 |

**대시보드 페이지 구성** (한 장 안 탭 넷) : ① 표 (작물 50종을 그냥 표로) ② 곡선 (비용·수입·성장시간을 한 그림에)
③ 경제 (30일 자원 잔고 · 원천÷배수구) ④ 뽑기 (기대 횟수 · 분포 · 천장까지 몇 번)

**안 만들 것** : 웹에서 고치기 · 로그인 · 서버 · 실시간 갱신 · 여러 사람 협업. 전부 우리에게 필요 없다.

## 7. 이 요청의 빈틈 · 보완할 점

사용자 결정(「스프레드시트 안 쓰고 자체 데이터 + 웹 대시보드」)은 방향이 맞다.
다만 아래 넷은 짚고 가는 게 낫다.

### ① 스프레드시트를 버리면 무엇을 잃나

잃는 것은 크게 둘이다. **근거 있는 잃음이다.**

- **값을 바꾸면 그 자리에서 다시 계산되는 손맛.** 게임 디자이너가 시트를 쓰는 가장 큰 까닭이
  「수식으로 스탯을 맞추고, 숫자 모델을 만들고, 설정을 바꿨을 때 영향을 눈으로 보는 것」이다
  [전언](https://medium.com/@urpi/spreadsheet-tools-in-game-design-57511eac68c).
  한 칸 값이 다른 칸들의 수식에 들어가 자동으로 다시 계산되는 것이 경제 조율의 기본 동작이다
  [전언](https://www.gamedeveloper.com/design/my-approach-to-economy-balancing-using-spreadsheets).
- **수식이 눈에 보이는 것.** 시트는 칸을 누르면 「이 숫자는 어디서 나왔나」가 바로 보인다.
  JSON 은 값만 보이고 식은 코드 안에 숨는다.

또 자주 인용되는 경고가 있다 —
**「전용 경제 툴을 만들고 유지하는 데는 엔지니어 시간이 든다. 툴은 게임과 함께 늙는다. 경제가 바뀔 때마다 툴을 고쳐야 한다」**
[전언](https://dev.to/hiroshi_takamura_c851fe71/best-game-economy-design-tools-for-modern-game-teams-30kp).

**대시보드가 이것을 어떻게 대신하나** [의견]

| 잃는 것 | 대신하는 방법 |
| --- | --- |
| 즉시 재계산 | `balance dash` 가 1초 안에 다시 굽고 브라우저가 새로고침한다. 「저장 → 명령 → 새로고침」 3초짜리 고리면 손맛의 8할은 산다. 파일 감시(`--watch`)를 붙이면 더 가깝다 |
| 수식이 보임 | **식을 데이터에 적는다** (`"formula": "base * pow(growth, level-1)"`). 대시보드가 식을 글자 그대로 보여 주고 그 옆에 곡선을 그린다. 오히려 시트보다 잘 보인다 |
| 한 칸 바꿔 보기 | 대시보드에 **읽기 전용 미리보기 슬라이더**를 둔다. 브라우저 안에서만 값을 흔들어 곡선이 어떻게 움직이나 보고, 마음에 들면 그 숫자를 AI 에게 말한다. **파일은 안 건드리니 저장 문제도 없다.** 이게 「보기만 웹」의 손해를 가장 크게 메운다 |

> **이건 꼭 넣기를 권한다.** 슬라이더 미리보기 하나가 「스프레드시트가 그리웠던 이유」의 대부분을 없앤다.

### ② 「웹에서 고치기」까지 만들면 공수가 얼마나 뛰나

[의견] 눈금이다. 실측 아님.

| | 보기만 (가 갈래) | 고치기까지 (나 갈래) |
| --- | --- | --- |
| 만들 것 | 데이터 읽기 · 검사 · 시뮬 · HTML 굽기 | + 로컬 서버 · 표 편집 UI · 값 검증 · 저장·되돌리기 · 충돌 처리(AI 도 같은 파일을 고친다) |
| 눈금 | **2.5일** | **6~8일** |
| 이후 유지 | 데이터 종류가 늘 때 페이지만 더함 | 편집 UI 도 같이 늘어남 — 종류마다 |
| 위험 | 낮다 | AI 편집과 웹 편집이 부딪힌다. 사람이 브라우저에서 고치는 동안 AI 가 같은 파일을 고치면 하나가 날아간다 |

**세 배쯤 뛴다.** 그리고 늘어나는 것은 「만드는 값」만이 아니라 **매번 고칠 값**이다.
**「가」로 시작하고, ①의 슬라이더 미리보기를 넣고, 그래도 답답하면 그때 「나」를 붙인다.**
데이터 폴더·스키마·굽기 코드는 그대로 쓰이니 버리는 게 없다.

### ③ 툴 만들기가 게임 만들기를 잡아먹는 위험

이건 실제로 잘 알려진 함정이다.
**「툴 만들기는 나중이 빨라진다는 이유로 정당화되지만, 대개 게임의 규모 자체를 키운다 —
시간을 아끼는 만큼 새 일도 만든다」** [전언](https://www.derekyu.com/makegames/archetypes.html).
같은 글이 「내 툴을 다음 게임이나 남이 쓸 것」이라는 기대도 거의 안 맞는다고 짚는다.
스코프 크립은 인디 게임이 안 끝나는 가장 큰 까닭 중 하나다 [전언](https://www.wayline.io/blog/scope-creep-indie-games-avoiding-development-hell).

**최소 구성 선** [의견] — 아래를 지키면 잡아먹히지 않는다.

- **툴 총 3일을 넘기면 멈춘다.** 3일에 안 끝나면 설계가 큰 것이다.
- **실제 수치가 생기기 전에는 안 만든다.** `Tools/GamedesignTool/Docs/Guide/기획절차.md` 8단계(세로 조각)에서 `04-수치표.md` 를 쓸 때가 시작점이다.
  그 전에는 만들 데이터가 없어서 상상으로 만들게 되고, 상상으로 만든 툴은 다 틀린다.
- **프로토타입 단계(5단계)에서는 툴 없이 간다.** 버릴 코드에 붙일 대시보드는 없다.
- **기능을 늘리고 싶어지면 「이걸로 게임의 어떤 물음에 답하나」를 먼저 적는다.** 못 적으면 안 만든다.

### ④ 프로토타입 갤러리·단계 대시보드와 합칠 수 있나

[의견] **뼈대는 같다. 그러니 「굽는 틀」은 하나로 하고, 페이지는 따로 만든다.**

셋 다 「저장소 파일을 읽어 → 정적 HTML 을 굽는다」로 똑같다.
공통인 부분은 이렇다 : 파일 훑기 · 마크다운·JSON 읽기 · HTML 틀(머리·탭·CSS) · 그래프 붙이기 · 한 장으로 묶기.
다른 부분은 **무엇을 읽고 무엇을 그리나**뿐이다.

| | 읽는 것 | 그리는 것 |
| --- | --- | --- |
| 수치 대시보드 | `Data/*.json` | 표 · 곡선 · 경제 흐름 · 뽑기 분포 |
| 프로토타입 갤러리 | `Prototypes/` 폴더 · 각 씬의 설명 | 목록 · 물음/판정 · 통과·불통 |
| 단계 대시보드 | `Docs/Todo/진행상황.md` · mem · EffortTool | 단계 진행 · 공수 예상 대 실제 |

**권고** : 툴은 **하나(가칭 `DashTool` 또는 `BalanceTool`)**, 명령은 `dash balance` · `dash proto` · `dash status` 처럼 나눈다.
결과는 **탭 셋을 가진 HTML 한 장**. 사용자가 여는 파일이 하나면 실제로 본다. 셋이면 하나만 본다.

**단, 합치는 결정은 다른 조사(프로토타입 갤러리·단계 대시보드)가 끝난 뒤에 한다.**
그쪽이 「매번 다시 구워야 하나 · 상시 떠 있어야 하나」에서 다른 답을 내면 합치면 안 된다.
지금 정할 것은 **「HTML 굽는 코드는 처음부터 다시 쓸 수 있게 따로 떼어 둔다」** 하나뿐이다.

## 못 찾은 것

- **CastleDB 공식 사이트(castledb.org)에 접속이 안 됐다.** 특징은 2차 자료로만 확인했다.
- **Machinations 의 정확한 가격**을 확인 못 했다. 무료 등급이 있다는 것만 봤다.
- **Observable Plot 의 실제 파일 크기** 숫자를 못 찾았다.
- **「데이터를 CLI 로 검증하고 결과를 정적 대시보드에 얹는」 게임 밸런스용 완성품**을 못 찾았다.
  없어서 못 찾은 것인지, 검색어가 나빴는지는 확실하지 않다.
- **Odin Inspector · BGDatabase 의 최신 가격·기능**은 직접 확인 안 했다 (우리 규칙상 어차피 탈락이라 얕게만 봤다).
- 이 문서의 **공수 눈금(2.5일 · 6~8일 · 3일 선)은 전부 의견이다.** 실측 근거가 없다.
