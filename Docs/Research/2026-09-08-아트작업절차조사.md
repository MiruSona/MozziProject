# 아트 작업 절차 조사

> 코드에 「조사 → 설계 → 작업」이 있듯 아트에도 단계별 구조가 있는지, 1인 개발자가 어떻게 줄여 쓰는지,
> PixelLab MCP + ArtTool 로 어떻게 이어지는지를 웹에서 조사한 문서.
> 날짜 2026-09-08 · 쓴 사람 AI (사용자 확인 전) · 상태 조사 1판

## 1. 결론 먼저

- **아트에도 표준 단계가 있다.** 큰 틀은 「준비(방향·규칙·목록) → 제작(캐릭터·타일·UI) → 통합·다듬기」 세 덩어리다.
  코드의 조사→설계→작업과 같은 꼴이다.
- **1인 개발은 「스타일 규칙 한두 장」 + 「에셋 목록」 두 산출물만 제대로 만들면 나머지는 짧게 줄여도 된다.**
  여러 글이 입을 모아 말하는 첫 실수는 「규칙 없이 캔버스부터 여는 것」이다.
- **픽셀아트는 규칙을 먼저 못 박아야 한다** — 기준 해상도·스프라이트 크기·팔레트·외곽선·시점. 하나라도 어긋난 그림 한 장이 전체를 깬다.
- **24종은 「베이스 12 + 팔레트 바꾸기 12」로 간다.** 이미 합성소 설계에서 「변종은 팔레트만 바꾼다」고 정했고, 업계 방식과 같다.
- **PixelLab MCP 는 「그리는 손」, ArtTool 은 「규격·검수·굽기」다.** 둘 사이에 사람이 Aseprite 로 손보는 자리가 꼭 하나 있다.
  AI 는 「여러 장 사이 일관성」과 「정밀한 애니메이션」이 약하다는 것을 여러 출처가 같이 말한다.

## 2. 2D 게임 아트 파이프라인의 표준 단계

여러 출처의 단계를 한 표로 합쳤다. (확인함 : 출처 ①②③)

| # | 단계 | 산출물 | 끝났다고 보는 기준 |
| --- | --- | --- | --- |
| 1 | 아트 디렉션 · 무드보드 | 참고 그림 모음, 「이런 느낌」 한 문장 | 두세 장의 기준 그림이 정해져 「이게 우리 톤」이라고 가리킬 수 있다 |
| 2 | 스타일 가이드(아트 바이블) | 규칙 한두 장 (3절) | 규칙만 보고 새 그림을 그려도 어긋나지 않는다 |
| 3 | 컨셉 | 주인공·핵심 물건 스케치 여러 안 | 실루엣만 봐도 알아보는 안이 골라졌다 |
| 4 | 키 아트 | 대표 장면 한 장 | 화면 전체 색·밀도 느낌이 확정됐다 (1인이면 건너뛰거나 첫 화면 목업으로 대신) |
| 5 | 에셋 목록 | 표 (이름·크기·프레임 수·상태) | 시스템 문서마다 필요한 그림이 한 줄씩 다 적혔다 |
| 6 | 캐릭터 스프라이트 · 애니메이션 | 시트 PNG | 규칙(크기·팔레트·프레임 수)을 통과하고 엔진에서 돌아간다 |
| 7 | 타일 · 배경 | 타일셋 · 배경 PNG | 이어 붙여도 이음새가 안 보이고 캐릭터와 같은 톤 |
| 8 | UI | 패널·버튼·아이콘 | 기준 해상도에서 정수 배율로 또렷하고 상태(누름 등)가 다 있다 |
| 9 | 엔진 통합 | 임포트 설정 · 아틀라스 · 애니 클립 | 게임에서 실제로 움직인다 |
| 10 | 폴리시 · VFX | 연출·효과 | 「제일 재밌는 순간」(도감 열림)에 연출이 붙었다 |

**1인·소규모가 줄이는 법** (확인함 : 출처 ④⑤⑥)

- 1~2 를 **한두 장짜리 규칙 문서**로 합친다. AAA 식 두꺼운 바이블은 필요 없다.
- 4(키 아트)는 **첫 화면 목업 한 장**으로 대신한다.
- **한 캐릭터를 끝까지** (스케치 → 스프라이트 → 애니 → 엔진) 먼저 통과시켜 절차를 검증하고, 그 다음에 수를 늘린다.
  이 프로젝트의 「첫 구현 편집 하나까지는 Opus 가 하고 그 다음을 넘긴다」 규칙과 같은 생각이다.
- 애니메이션은 **맨 마지막**. 핵심 포즈 2~3장부터 만들고 중간 프레임은 나중에.

## 3. 스타일 가이드(아트 바이블)에 담을 것

한두 장이면 된다. 아래는 여러 출처에서 겹치는 항목이다. (확인함 : 출처 ⑥⑦⑧⑨)

| 항목 | 정해야 하는 것 | 이 게임 상태 |
| --- | --- | --- |
| 기준 해상도 | 화면 논리 해상도. 16:9 는 320×180 · 640×360 이 표준 (1080p 의 정수 배) | **안 정함** — 세로 화면이라 180×320 처럼 뒤집어야 한다. 출처 ⑧은 세로를 다루지 않는다 (추측) |
| 배율 규칙 | 정수 배율만 · 남는 자리 검게 | ArtTool 프로필 기본이 `integer` + `letterbox` |
| 스프라이트 크기 | 16 · 24 · 32 · 48 중 하나. 크기 두 배 = 일 네 배 | **안 정함**. 32 가 「균형점」, 48 은 PixelLab 기본값 |
| 타일 크기 | 16 또는 32. 캐릭터와 깔끔한 배수 관계 | **안 정함** |
| PPU | 타일 크기와 맞춤 (타일 16 = PPU 16) | 타일 크기 따라감 |
| 팔레트 | 한 팔레트를 모든 그림에. 스프라이트당 4~16색 | 아바타 색표로 잡기로 함 (mem 20260907-a9bf4d21). 찹쌀이 자체 색은 **안 정함** |
| 외곽선 | 1px 검정 · 색 외곽선 · 없음 중 **하나만** | **안 정함** |
| 명암 | 평면 · 2~3단 셀 · 그라데이션. 그림자는 차갑게 하이라이트는 따뜻하게(hue shift) | **안 정함** |
| 시점 | 탑다운 · 낮은 탑다운(3/4) · 사이드 | **안 정함**. 농장 게임은 보통 낮은 탑다운 |
| 비율 | 머리 몇 등신, 보스 배율 | 찹쌀이는 덩어리라 등신 개념 대신 「몸 대비 왕관 크기」를 정하면 된다 (추측) |
| 애니 규칙 | 기본 프레임 길이(예 80ms), 동작별 프레임 수(예 idle 4 · walk 6) | **안 정함** |
| 빛 방향 | 왼쪽 위 등 한 방향 고정 | **안 정함** |
| 하지 말 것 | 「좋은 예 / 나쁜 예」 나란히 한 장 | 만들 것 |

**픽셀아트에서 제일 먼저 못 박을 셋** : 기준 해상도(배율) · 스프라이트/타일 크기 · 팔레트. 이 셋은 나중에 바꾸면 그림을 다 다시 그린다.
외곽선·명암은 그 다음이다.

## 4. 캐릭터가 많은 게임(합성·도감형)의 관리법

(확인함 : 출처 ⑩⑪⑫)

| 방법 | 내용 | 이 게임 적용 |
| --- | --- | --- |
| 베이스 + 팔레트 바꾸기 | 기본 그림 하나를 색 묶음(몸·장식·눈)으로 나눠 색만 바꿔 변형을 만든다 | **빛나는 변종 12 = 일반 12 의 팔레트 바꾸기.** 합성소 설계 9절과 일치 |
| 색 묶음을 따로 둔다 | 같이 바뀌면 안 되는 부위끼리 같은 색을 쓰지 않는다 | 몸 · 왕관 · 눈·볼 · 계열 장식은 서로 다른 색값으로 |
| 인덱스 팔레트 · 런타임 LUT | 그림은 한 장, 팔레트만 갈아 끼운다 | ArtTool 프로필 `palette.swap: runtime_lut` 가 이미 이 방식 |
| 애니메이션 공유 | 색 매핑을 프리셋으로 저장해 걷기·쉬기 모든 애니에 같이 적용 | 계열 안 3단계는 형태가 다르니 애니는 단계별로, 변종은 애니 공유 |
| 희귀 변형은 색을 더 세게 | 초반 변형은 색조만, 희귀는 극적인 색 또는 이야기와 묶기 | 빛나는 변종은 팔레트 + 반짝 효과(연출) 로 |

24칸을 그림 수로 셈하면 : **베이스 12장 × 방향 수 × 애니 프레임**이 진짜 작업량이다.
예로 방향 4 · idle 4 프레임 · walk 6 프레임이면 12 × 4 × 10 = 480 프레임. 방향을 2(좌우 뒤집기)로 줄이면 반이다.
방치형 농장은 「돌아다니는」 것보다 「자리에서 꿈틀」이 많으니 방향 수를 줄이는 것이 첫 절감이다 (추측 — 프로토타입에서 확인).

## 5. AI 보조 픽셀아트 파이프라인 — PixelLab MCP

### PixelLab MCP 가 정확히 무엇인가 (확인함 : 출처 ⑬⑭⑮)

- **원격 HTTP MCP 서버**(`https://api.pixellab.ai/mcp`)다. npm 패키지가 아니고, 계정의 bearer 토큰으로 붙는다.
  stdio 만 되는 클라이언트는 `npx mcp-remote@latest` 로 다리를 놓는다. 공식 저장소는 `github.com/pixellab-code/pixellab-mcp`.
- 같은 계정 자산을 **웹 앱 · Aseprite 확장 · MCP · Python API** 네 길로 다룬다.
- 요금은 「생성(gen)」 단위. 문서 예시로 1 gen ≈ $0.01, `get_balance` 로 잔액 확인. **가격표 자체는 문서에서 못 봤다.**

핵심 도구 (도구 이름은 공식 문서 그대로) :

| 갈래 | 도구 | 무엇을 하나 | 비용 눈금 (문서값) |
| --- | --- | --- | --- |
| 캐릭터 | `create_character` | 설명 → 4 또는 8방향 스프라이트. `size` 16~256 (기본 48), `view` 낮은/높은 탑다운·사이드, `outline`·`shading`·`proportions` 선택 | standard 1 gen · v3 2~9 gen · pro 20~40 gen |
| 회전 | `create_character` v3 + `reference_image_base64` | **내가 그린 한 장을 8방향으로 돌린다** | v3 값 |
| 변형 | `create_character_state` | 기존 캐릭터에 「빨간 갑옷」 같은 편집을 모든 방향에 일관되게. `use_color_palette_from_reference=True` 면 원본 팔레트 고정 | 20~40 gen |
| 애니 | `animate_character` | 템플릿(walk·idle 등 40개+) · 글 설명(v3, 4~16 짝수 프레임) · pro | 방향당 1 gen ~ 40 gen |
| 타일 | `create_topdown_tileset` | Wang 16타일 지형 + 경계 | — |
| 물건 | `create_map_object` · `create_object_state` | 설비·소품, 변형(이끼 낀·금빛) | — |
| UI | `create_ui_asset` · `create_font` | 패널 · 픽셀 글꼴 | — |
| 뒷정리 | `reduce_colors` · `correct_pixelart` · `unzoom_image` | **공용 팔레트로 색 줄이기** · 튀는 픽셀 정리 · 배율 되돌리기 | 0.1 gen |
| 일관성 | `style_image_base64` · `style_object_id` | 기존 그림을 스타일 참조로 넘긴다 | — |

주의할 것 (문서에 적힌 것) : 생성은 비동기(캐릭터 2~5분)라 `get_*` 로 폴링한다. 32×32 넘는 그림은 base64 대신 `*_url` 로 넘긴다.
`body_type` 은 humanoid 또는 quadruped(곰·고양이·개·말·사자 템플릿)뿐이라 **찹쌀이 같은 덩어리는 humanoid + chibi 비율로 흉내 내거나
`create_image_*` 자유 생성 + v3 회전으로 가야 한다** (추측 — 써 봐야 안다).

### Aseprite 와 어떻게 잇나

- PixelLab 은 **Aseprite 확장**을 따로 낸다 (출처 ⑭). 같은 계정 자산을 Aseprite 안에서 부른다. 상세 페이지는 이번에 못 읽었다.
- 별개로 `willibrandon/pixel-mcp` 는 **로컬 Aseprite 를 AI 가 조작**하는 MCP 다 (그리기·애니·팔레트·시트 내보내기, Aseprite 1.3+ 필요). PixelLab 과 다른 물건이다.
- ArtTool 에는 `sprite/aseprite` 감싸기 코드가 있지만 **이 PC 에 Aseprite 가 없어 계약만 시험했다** (ArtTool README).

### 한계 (여러 출처가 겹치는 것 — 출처 ⑯⑰)

| 한계 | 대응 |
| --- | --- |
| 여러 장 사이 스타일 일관성이 흔들린다 | 첫 캐릭터를 사람이 손봐 「기준 그림」으로 만들고 `style_*` 참조로 넘긴다. `reduce_colors` 로 팔레트 고정 |
| 정밀한 애니메이션이 약하다 | 핵심 포즈만 AI, 중간 프레임과 수정은 Aseprite |
| 프롬프트 한 번에 원하는 것이 안 나온다 | 10~20장 뽑아 실루엣으로 2~3장 고른다 (출처 ⑰의 절차) |
| 캔버스·격자 어긋남 | ArtTool `normalize` → `check` 로 잡는다 |

## 6. 이 프로젝트에 맞춘 제안 단계표

코드의 조사 → 설계 → 작업에 맞춰 **아트도 셋**으로 간다. 기획 9단계와의 자리도 적었다.

| 아트 단계 | 코드 단계에 견주면 | 기획 9단계 중 언제 | 산출물 | 끝 기준 |
| --- | --- | --- | --- | --- |
| A. 방향 (조사) | 조사 | 지금 (5단계 옆에서) | 무드보드 · **아직 안 정한 결정 목록에 답** · 첫 화면 목업 1장 | 사용자가 6절 표의 결정을 다 내렸다 |
| B. 규칙 (설계) | 설계 | 7단계(기능 자르기) 전후 | `Docs/Design/06-아트규칙.md` 한두 장 · ArtTool 프로필 · 팔레트 JSON · **에셋 목록** | 흰찹쌀이 한 마리가 A→PixelLab→Aseprite→ArtTool→Unity 를 끝까지 통과했다 |
| C. 제작 (작업) | 작업 | 8단계(세로 조각)부터 | 12 베이스 → 변종 12 → 설비·타일 → UI → 연출 | 에셋 목록의 상태 칸이 다 「굽힘」 |

- **B 의 끝 기준이 핵심이다.** 규칙 문서만으로 끝내지 않고 한 마리를 끝까지 통과시켜야 프로필 값(크기·baseline·마커)이 진짜로 맞는지 안다.
- 기획 9단계에는 아트 단계가 없다. **정본(`Tools/GamedesignTool/Docs/Guide/기획절차.md`)에는 손대지 않고**, 이 게임 문서 뼈대에 `06-아트규칙.md` 한 줄을 더하는 것을 제안한다. 파일 번호는 제안이고 사용자가 정한다.

### 사용자가 정해야 할 결정 (A 단계)

| # | 결정 | 고를 것 | 왜 먼저인가 |
| --- | --- | --- | --- |
| 1 | 그림 갈래 | 픽셀아트 · 벡터/손그림 | PixelLab·ArtTool 둘 다 픽셀 전제. 아니면 툴이 바뀐다 |
| 2 | 기준 해상도 (세로) | 예 180×320 · 270×480 · 360×640 | 배율·UI·타일 수 전부 여기서 나온다. 세로 표준은 출처에 없어 실측 필요 |
| 3 | 시점 | 낮은 탑다운(3/4) · 사이드 | 농장 바닥과 찹쌀이 방향 수를 정한다 |
| 4 | 찹쌀이 크기 | 32 · 48 | 32 = 일 1/2, 48 = PixelLab 기본. 도감 그림은 따로 크게 뽑아도 됨 |
| 5 | 타일 크기 | 16 · 32 | PPU 와 같이 |
| 6 | 팔레트 | 아바타 색표 안에서 찹쌀이 몸·왕관·계열 4색 묶음 | 변종 = 팔레트 바꾸기라 색 묶음 설계가 곧 도감 설계 |
| 7 | 외곽선 · 명암 | 1px 검정/색/없음 · 평면/2~3단 | 섞으면 티가 난다 |
| 8 | 방향 수 | 1(정면만) · 2(좌우) · 4 | 작업량의 배수. 방치형이라 1~2 로 갈 수 있는지 |
| 9 | 애니 최소 | idle 만 · idle+walk · +happy(도감 열림) | 프레임 수 규칙까지 |
| 10 | 빛 방향 | 왼쪽 위 등 | 설비·타일과 캐릭터가 같아야 함 |
| 11 | AI 비중 | 베이스도 AI · 베이스는 손 + 회전/변형만 AI | 예산(gen)과 일관성의 저울 |

## 7. 추측과 확인한 것 나누기

- **확인함** : 2~5절의 표 내용, PixelLab 도구 이름·인자·비용 눈금(공식 MCP 문서), ArtTool 프로필 항목(저장소 파일).
- **추측** : 세로 화면 기준 해상도 후보, 덩어리 캐릭터를 PixelLab 으로 뽑는 방법, 방향 수를 줄일 수 있다는 것, 프레임 수 예시. 전부 B 단계 실험에서 확인한다.
- **못 읽은 것** : PixelLab Aseprite 확장 상세 페이지, PixelLab 가격표, Ansimuz 의 1인 개발 팁(403).
